# Развёртывание: проверяемые шаблоны, не запущенный сервис

В репозитории находятся Docker Compose, Dockerfile и systemd-шаблон для отдельного worker. Они добавлены в ходе интеграции revisions, но контейнерная сборка и установка systemd в текущей Windows-среде не выполнялись: Docker/systemd здесь не обнаружены. Для отдельных конкурентных проверок подготовлен временный portable PostgreSQL 16.14 на loopback, без установки службы и без pgvector; полный migration/search-контракт проверяется в PGlite с расширениями. Локально также проверяются исходный build, структура YAML и чистая установка зависимостей; это не доказательство внешнего deployment.

## Воспроизводимость

`package-lock.json` фиксирует граф зависимостей. Используйте Node.js из `.node-version` (22.23.3 LTS); поддерживаемый диапазон `>=22.23.2 <23` включает управляемый Vercel patch 22.23.2. Текущий Next.js — `~16.4.2`, ESLint — `10.13.0` с нативными React/a11y/import-плагинами. Чистые установки и локальные production-сборки описаны в [стабилизации Node/PGlite](v8-pglite-stability-2026-10-18.md), [совместимости Vercel](vercel-node22-compatibility-2026-10-18.md) и [политике ESLint](react-eslint-native-policy-2026-10-18.md). Сверяйте версии с `package.json` и lockfile; старые протоколы установки относятся к своим датам.

Основной workflow `Chronicle verification` запускает независимо typegen/typecheck и lint, полный набор unit/PGlite-тестов в четырёх изолированных job, native PostgreSQL-проверки с применением миграций и повторным прогоном, production build. Каждый job устанавливает зависимости через `npm ci --ignore-scripts`. Внутри каждого тестового shard сохранён `--test-concurrency=1`; распределение файлов выполняет Node.js через `--test-shard=N/4`. Итоговый check `verify` принимает только успешный результат всех основных job: failure, cancellation или skipped не превращаются в успех.

Отдельный workflow `Chronicle supplementary checks` на каждом push/PR и при ручном запуске проверяет документацию, карту и диалоги в Chromium/Firefox/WebKit, браузерные latency/fixture-сценарии, повтор запросов и обновление service worker, полный Next lifecycle/modals. Эти проверки сохраняют собственный красный результат при ошибке, но не входят в зависимости `verify`. Для lifecycle используется отдельная PostgreSQL+pgvector БД и production-сервер на loopback; readiness, скриншоты и server log сохраняются как CI evidence. Two-build update suite выполняется в другом job, чтобы её сборки не перезаписывали артефакты работающего lifecycle-сервера. Секреты пользователя CI не нужны.

Vercel Git deployment работает отдельно от этих workflow; обязательный `build:deploy` по-прежнему выполняет миграции и сборку, а их ошибка блокирует деплой. По удалённым результатам проверки 23 октября 2026 года Production deployment завершался и до окончания `verify`, и при его ошибке; GitHub branch protection/rulesets для `main` отсутствовали. Если оператор позже включит Vercel Deployment Checks, для основного CI предназначен стабильный check `verify`; дополнительные checks выбираются отдельно. Наличие файлов workflow не подтверждает успешность конкретного удалённого запуска.

Unit-тесты не загружают `.env`, используют недоступный dummy DATABASE_URL для импорта модулей, PGlite-fixtures и синтетические ключи. Это предотвращает случайное использование унаследованных credentials; это не сетевой sandbox. Live-evaluation и отдельные smoke-скрипты остаются самостоятельными, явно настроенными операциями.

`npm run verify:revisions-ui` запускается только с `CHRONICLE_UI_ISOLATED=1` и `SMOKE_BASE_URL` на loopback. Нужен уже работающий сервер с отдельной одноразовой БД и без provider credentials. Скрипт создаёт синтетические аккаунты/кампании и оставляет их в этой БД для анализа; пользовательская БД недопустима. На production-сборке проверяются реальные HTTP-переходы гостя/аккаунта, явный перенос, запреты ролей, JSON download/upload, контекстные команды и модальные окна. Старые `verify:story-ui`/`verify:ui` дополнительно проверяют интерфейс с mock API; они не заменяют реальные серверные проверки.

## Vercel и Neon

Для текущей production-БД Neon во Frankfurt функции закреплены в `vercel.json` → `regions: ["fra1"]`. Этот файл переопределяет регион по умолчанию в dashboard; при переносе БД нужно согласованно изменить регион и выполнить новый deployment. Проверять следует фактический `X-Chronicle-Region`, отдельный регион proxy и распознанный `X-Chronicle-Database-Region`, а не только настройки проекта. Статические файлы обслуживает глобальный CDN.

Миграции выполняет обязательный `build:deploy`; дублирующий `CHRONICLE_AUTO_MIGRATE=1` для этого окружения не нужен. Runtime использует общий pg pool (`max=10`, `min=0`, idle 10 секунд, получение соединения до 10 секунд) и однократный lifecycle hook Fluid. Таймаут получения не является таймаутом SQL/транзакции. Прогрев SQL-пингами и отключение приостановки Neon не входят в конфигурацию. [Причины, production-замеры и границы](database-cold-entry-production-2026-10-19.md).

## Docker Compose

Файлы: [Dockerfile](../deploy/docker/Dockerfile), [Compose](../deploy/docker/docker-compose.yml), [.dockerignore](../.dockerignore).

Перед запуском оператор:

1. Задаёт `CHRONICLE_DB_PASSWORD`: случайный URL-safe пароль, например случайные байты в hex-представлении. Значение используется и PostgreSQL, и URL соединения; произвольные `@`, `:`, `/` потребуют отдельной корректной URL-кодировки, поэтому этот шаблон требует URL-safe значение.
2. Настраивает `CHRONICLE_SECRET_KEYS` и `CHRONICLE_SECRET_ACTIVE_KEY` по [инструкции секретов](secret-storage-operations.md). Без keyring возможна игра без AI, но сохранение непустого API-ключа запрещено.
3. Планирует backup/restore для постоянного тома БД. Не удаляет том при обычном обновлении.
4. Только после проверки окружения запускает из корня проекта:

   ```sh
   docker compose -f deploy/docker/docker-compose.yml up --build -d
   ```

Compose запускает PostgreSQL с pgvector → отдельный migration job → web → worker после HTTP readiness. При неуспешной миграции web не стартует. Startup-миграции в этом шаблоне выключены, поскольку есть отдельный migration job. PostgreSQL не публикует порт на хост; web привязан только к `127.0.0.1:3000`. Для внешнего доступа оператор отдельно настраивает HTTPS reverse proxy и доверие его заголовкам.

Healthcheck использует `node`/`fetch`, которые есть в Node image; он не зависит от отсутствующего `wget`. Runtime работает под непривилегированным пользователем `node`. Локальные `.env`, revisions, git и execution artifacts исключены из build context; реальные credentials передаются окружением, не запекаются в образ.

Если ранее уже существовал том БД, смена `CHRONICLE_DB_PASSWORD` в окружении не меняет автоматически пароль в PostgreSQL. Смена DB credential — отдельная операторская процедура, не «повторный up».

## Отдельный worker через systemd

Шаблон: [chronicle-worker.service](../deploy/systemd/chronicle-worker.service). Он не установлен автоматически. Оператор должен подготовить системного пользователя `chronicle`, приложение в `/opt/chronicle`, Node по указанному пути и защищённый `/etc/chronicle/worker.env`.

EnvironmentFile содержит DATABASE_URL и тот же keyring/серверные настройки, что у web. Не выдавайте worker больше прав БД/ОС, чем нужно. Применяйте миграции отдельным проверенным шагом до запуска либо явно включите описанный [startup-режим](worker-operations.md#опциональные-миграции-при-запуске).

Worker запускается непосредственно через `node --import tsx scripts/memory-worker.ts`, без требования положить `.env` внутрь приложения. Установлены UTC, ограничительные параметры systemd и 90 секунд на завершение текущего ограниченного задания после SIGTERM. Конкретные пути и sandbox-параметры проверяются на целевом Linux; наличие файла не доказывает пригодность для любого хостинга.

## Что проверить на целевом окружении

- Чистая БД и повтор миграций; восстановление из резервной копии.
- Web readiness, вход гостем и аккаунтом, административные границы, отсутствие секретов в ответах.
- Запуск worker после закрытия браузера, перезапуск, два экземпляра с независимыми heartbeat, lease expiry и отказ провайдера.
- Квоты и owner-specific credentials; отсутствие использования ключа администратора вместо пользовательского без явного контракта.
- HTTPS/cookies, доверенные proxy headers, лимиты БД, наблюдение за backlog.

Публичный доступ нельзя считать подготовленным только по успешному build или наличию контейнерных файлов. Игровая функциональность и права должны пройти итоговую интеграционную проверку.
