# Первый вход: регионы, подключение и пул, 19.10.2026

Продолжение [предыдущего production before/after](database-latency-production-2026-10-19.md). Проверка разрешена владельцем для `https://rpgtoku.vercel.app` и настоящей БД. Используется отдельный технический аккаунт без кампаний, прав администратора и ключей провайдеров; платных AI-запросов нет.

## Подтверждённые причины и границы

- Настройки Vercel показывали Fluid Compute и функции в `iad1` (США). Проект Neon, подключённый к приложению, находится в AWS Europe Central 1 / Frankfurt (`fra1`). Это подтверждено отдельно в Vercel integration settings и Neon Console.
- Runtime диагностического релиза подтвердил `iad1`, proxy — `fra1`. `CHRONICLE_AUTO_MIGRATE` выключен: миграции при старте не объясняют наблюдавшиеся задержки. Обязательный deploy migration остаётся отдельным шагом сборки.
- `pg-pool` закрывает все простаивающие соединения через 10 секунд (`min=0`). После 15 секунд снова создаются физические соединения при `Instance-First=0`: задержка подключения воспроизводится даже в уже работавшем JS-контексте.
- Три тёплых bootstrap гостя занимали 887–910 мс HTTP / 657–663 мс `app`, аккаунта — 983–1135 / 750–752 мс; новых соединений и очереди не было. Следовательно, остаются и последовательные проходы к удалённой БД. Увеличение максимального размера пула не устраняет этот путь.
- Neon Console: один primary compute, 0.25 CU, scale-to-zero после 5 минут неактивности. Это отдельная граница от idle timeout клиентского пула. Принудительная приостановка/перезагрузка рабочей БД не выполнялась.
- До исправления production singleton записывался в `globalThis` только вне production. Новые копии модуля могли создавать отдельные пулы в одном JS-контексте; регрессионная проверка воспроизводит это через повторную загрузку настоящего модуля.
- Первое создание настроек выполняло SELECT → INSERT → SELECT. Возврат строки через INSERT RETURNING убирает один проход; при конфликте с другим создателем остаётся отдельный свежий SELECT.

## Методика

Исходная серия: 19.10.2026, 10:42:58–10:46:13 UTC; build `317702ca-076c-4c19-8937-b4fec19ac9ee`, source `c339724`. Для гостя и аккаунта по 10 новых BrowserContext, 10 повторных навигаций, 10 сохранений и по 5 отдельных API-проб. Версии в начале и конце совпали, ошибок нет. DNS/TLS браузера относятся к клиенту/CDN, а не к подключению PostgreSQL.

Первые открытия измеряются от начала `page.goto` до готовности пространства с данными. Сохранение — от клика до завершённого canonical POST и готовой кнопки. После каждого измеренного сохранения отдельный GET подтверждает запись; он исключён из временного окна и прогревает следующие пробы. Обе группы используют тот же технический аккаунт до и после; настройки восстанавливаются и проверяются чтением.

Новый BrowserContext не означает холодную функцию или БД. Отдельная диагностическая серия на source `76afada`, build `90cac18f-9967-474b-9f6a-a392f75a0a17` измеряет новые подключения, тёплые запросы и запросы после пауз. Полное время HTTP включает транспорт, proxy и подготовку ответа. `app` начинается после загрузки обработчика; `Instance-First` отмечает первую инструментированную попытку, но не измеряет платформенный cold start. [Семантика метрик](performance-observability.md#что-означают-числа).

Наблюдённая очередь 2 при создании трёх соединений не доказывает исчерпание `max=10`; тёплая очередь равна 0.

После последнего DB-запроса в 10:49:25 UTC инструменты не обращались к приложению. Оба локальных таймера начали шестиминутное ожидание в 10:51:31.017–.018 UTC. В 10:55–10:56 UTC Neon Console дважды показал `SUSPENDED`; после запросов — `ACTIVE / Started: A few seconds ago`. Статус наблюдался через control plane, без SQL или принудительного рестарта.

Оба GET bootstrap отправлены в 10:57:31.036 UTC, спустя 360015 мс таймера и около 8 минут 6 секунд после предыдущей серии. Гость: HTTP 4182 / app 1913 / proxy 317 мс, аккаунт: HTTP 4276 / app 1980 / proxy 794 мс. У каждого `Instance-First=1`, три новых соединения; `db_connect` 1753/1766 мс. Это одно общее пробуждение БД с двумя одновременными посетителями, а не две независимые серии cold start. Одновременно холодны БД, соединения и контексты функций; разница HTTP и app включает сеть, proxy, загрузку модулей и платформу, поэтому её нельзя объявить временем запуска Neon.

## Исправления

Регион функций закреплён в `vercel.json` как `fra1`, рядом с Neon. Депрецированный в установленном Next.js 16.4.2 `preferredRegion` не используется. Static CDN остаётся глобальным.

Пул общий для всех загрузок модуля внутри JS-контекста во всех режимах. `attachDatabasePool` из публичного узкого экспорта `@vercel/functions/db-connections` регистрируется один раз. Он даёт таймерам pg завершить закрытие idle-соединений перед приостановкой Fluid. Сохранены `max=10`, `min=0`, idle timeout 10 секунд. Получение соединения ограничено 10 секундами; общий query/statement timeout не вводится, семантика транзакций и подтверждения записи сохраняется.

`min=0` выбран осознанно: опубликованный helper 3.10.1 ожидает idle-таймер pg, но сам не закрывает последнего клиента при `min=1`. Фоновые SQL-пинги, увеличение времени активности и отключение scale-to-zero не нужны. INSERT RETURNING возвращает каноническую новую строку на момент INSERT; конкурирующий создатель сохраняет свои значения, credentials и timestamp.

Это две небольшие пары по одному общему пробуждению до/после. Улучшение полного времени в этих наблюдениях — около 37–38%; это не оценка p95 независимых холодных запусков. Остаток HTTP вне app остаётся значительным, поэтому нулевой cold start не заявляется. В него входят proxy (в том числе первое обращение к приостановленной БД), транспорт, загрузка модулей и подготовка функций. Величина этого остатка не доказывает вклад отдельного импорта. Возможное сокращение графа Gemini/embeddings в bootstrap исследовано на уровне модулей, но не включено в поставку без подтверждённого выигрыша latency; текущий SQL/региональный эффект измерен отдельно.

## Проверки и оставшиеся ограничения

Локально на Node 22.23.2: production build, полный ESLint, 11 проверок пула/диагностики/Server-Timing, 12 регрессий настроек/секретов/bootstrap и 12 проверок owner/identity/bootstrap проходят. Новые проверки cold-creation и production pool reload сначала воспроизвели ошибку до исправлений. Изолированные fixtures не используют рабочую БД или настоящие provider keys.

Первый параллельный локальный запуск полного suite/build/lint исчерпал Windows commit limit: один тестовый subprocess завершился из-за памяти; сбой PostCSS worker перестал воспроизводиться после чистой сборки. Неполный локальный прогон остановлен и не учитывается как успешный. Линтер, сборка с чистым cache и затронутые тесты повторены последовательно и проходят.

Полный [CI run 39241283044](https://github.com/Le-Who/RPG_arena/actions/runs/39241283044) на точном code commit `4d637b256edad0d0221f3007e19cb77b4678cfce` завершён **success**: 1246 unit, 38 native PostgreSQL, 174 map/dialog executions трёх браузеров, 44 workspace/settings/draft checks, fresh/replay migrations, build, actual-handler retry и two-build PWA rollout. Все четыре jobs успешны. Production deployment этого commit также success: [поставленная версия](https://rpgtoku-p8l0unh8p-63174.vercel.app), canonical site — [rpgtoku.vercel.app](https://rpgtoku.vercel.app). Финальные документы и числовой артефакт проверены отдельно.

Не измерены отдельный платформенный init/span, независимая большая серия холодных запусков и задержки пользователей из разных частей мира. Публичная оболочка по-прежнему доступна до данных, а доступ к кампаниям и успешное сохранение требуют серверного подтверждения. Гарантии отсутствия холодного старта или границы latency для каждого посещения не вводятся.
