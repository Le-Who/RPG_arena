# Обновление открытого приложения

Приложение проверяет идентификатор сборки независимо от service worker. Новая версия показывает ненавязчивое уведомление «Доступна новая версия» с кнопками «Обновить приложение» и «Позже». Автоматической перезагрузки нет: открытые вкладки могут продолжать работать, обновление одной вкладки не перезагружает остальные.

## Защита пользовательского ввода

Перед перезагрузкой проверяется доступность сервера, текущий профиль и загрузка страницы. Незавершённый запрос хода, включая восстановление после ошибки, генерация, сохранение памяти, открытые диалоги и формы блокируют обновление. Обновить приложение можно на обзоре или в комнате истории; на других страницах сначала нужно сохранить изменения и вернуться на обзор. Это консервативная граница для форм, у которых пока нет общего протокола сохранения.

Черновик действия сохраняется вместе с ID-привязками предметов в `sessionStorage` текущей вкладки непосредственно перед перезагрузкой. Запись ограничена длиной текста, количеством привязок и сроком 24 часа. Восстановление однократное и только при совпадении профиля, кампании и подтверждённого владельца. Смена профиля очищает запись. Незавершённый запрос хода имеет приоритет над черновиком. Если непустой черновик нельзя записать и прочитать обратно, перезагрузка отменяется с объяснением. Это временное сохранение для добровольного обновления, не постоянное автосохранение редактора и не синхронизация вкладок.

Проверка версии запускается в production после загрузки, при возвращении на вкладку/восстановлении сети и раз в пять минут в видимой вкладке. Повторные фоновые проверки ограничены интервалом 30 секунд; одновременно выполняется не более одной, тайм-аут — шесть секунд. Нажатие кнопки запрашивает свежую проверку. Ошибка сети не очищает ввод и не запускает цикл перезагрузок.

## Сборка и развёртывание

`next.config.ts` создаёт идентификатор сборки и передаёт одинаковую строку в Next `generateBuildId` и компилируемую константу `APP_BUILD_ID`. Автоматический seed устанавливается до нормализации config и наследуется дочерними процессами сборки: повторная загрузка config не создаёт другую версию. При production start phase-aware config читает authoritative `.next/BUILD_ID` рядом с config; startup overrides не меняют готовый артефакт. ID присутствует в HTML (`meta[name="chronicle-build"]`), клиентском коде, `GET /api/version` и тексте `/sw.js`. Endpoint версии возвращает только `{buildId}` с `Cache-Control: no-store`; ему не нужны identity, cookies или БД.

Обычно ID создаётся автоматически. Для воспроизводимой поставки можно установить `CHRONICLE_BUILD_ID` **при сборке**: 1–128 букв ASCII, цифр, `_` или `-`. Разные поставки должны иметь разные ID. На все реплики выпускается один и тот же готовый артефакт сборки. Изменение переменной только при запуске не меняет уже скомпилированную версию. Не используйте один постоянный ID для разных исходников: это отключит обнаружение обновлений и обновление публичной оболочки. При rolling deployment смешанные версии реплик могут давать чередующиеся ответы; требуются согласованная маршрутизация выпуска и сохранение старых ассетов на стороне хостинга.

CDN/reverse proxy должен сохранять запрет кэширования `/api/version` и `/sw.js`. Проверка версии сообщает о новом выпуске, но не является проверкой здоровья БД или готовности провайдера.

## Политика service worker

Worker генерируется маршрутом `/sw.js` из `src/lib/service-worker-source.ts`; его текст меняется с каждой сборкой. Регистрация использует `updateViaCache: "none"`. Установка сначала загружает свежие `/offline.html`, `/icon.svg` и две PNG-иконки; при ошибке установки прежний worker остаётся активным. После успешной установки `skipWaiting()` и `clients.claim()` позволяют активироваться без закрытия всех вкладок. Они не перезагружают открытые документы.

Публичная офлайн-страница и иконки имеют кэш конкретной сборки; сохраняются текущая и одна предыдущая оболочка. Хешированные `/_next/static/` используют общий кэш максимум на 160 записей, поэтому активация нового worker не удаляет сразу чанки старых вкладок. Поддержана миграция разрешённых ассетов из прежних `chronicle-shell-v1/v2-static`. Переполнение CacheStorage не превращает успешный сетевой ответ в ошибку загрузки.

HTML приложения, RSC, API, приватные данные, query-варианты и сторонние адреса не сохраняются. Офлайн-навигация показывает публичную страницу из кэша текущего worker. Это не офлайн-игра и не приватная полка кампаний; для чтения без сети остаётся скачанная HTML-книга.

Кэш ограничен и может быть очищен браузером. Старый чанк, который вкладка никогда не загружала, может отсутствовать после развёртывания. Worker сообщает о недоступном ассете, чтобы предложить безопасное обновление, но не может восстановить удалённый файл. Для длительной поддержки старых вкладок хостинг должен сохранять ассеты нескольких выпусков; клиентский кэш не заменяет это требование. Вкладки, открытые до внедрения механизма уведомления, получат его после обычной перезагрузки.

## Проверка

Дополнение 09.10.2026: actual Next loader parent/child и persisted-server identity получили RED/GREEN регрессии; отдельно выполнены настоящая автоматическая production-сборка и два start, второй с конфликтующими `CHRONICLE_BUILD_ID`/`NEXT_PUBLIC_CHRONICLE_BUILD_ID`. Artifact/HTML/API/SW ID совпали, client comparison показал уведомление на чужом ID и убрал его на настоящем; page errors пусты. Это start/restart parity одного артефакта, не повтор исторического two-build rollout. [Текущий аудит и границы](test-coverage-audit-2026-10-09.md).

`tests/build-version.test.ts`, `tests/pwa-cache.test.ts` и `tests/update-draft.test.ts` проверяют контракты версии, политику кэша, миграцию, ограничения и сохранение черновика. `scripts/app-updates-browser.ts` строит два настоящих production-выпуска и переключает сервер под двумя открытыми вкладками одного origin. API кампаний заменены синтетическими ответами; тестовый reverse proxy убирает cookies, а сервер использует недоступную loopback БД. Скрипт проверяет разные версии worker, отсутствие самовольной перезагрузки, сохранение старого чанка, обновление одной вкладки, восстановление текста и привязки предмета, мобильную ширину и отсутствие приватных записей в CacheStorage. Логи и снимки — `output/playwright/app-updates/`.

`scripts/app-update-guards-browser.ts` проверяет настоящий React provider и восстановление запроса в отдельном production-fixture: отказ хранилища, офлайн, отложенное обновление, клавиатуру, мобильную ширину и гонку начала хода во время сетевой проверки. При ревью исправлены преждевременное удаление черновика до разрешения pending и блокировка обновления зависшим устаревшим запросом профиля. Совместное присутствие pending и черновика проверено также в настоящем PlayRoom: до «Отложить действие» запись сохраняется, после — восстанавливается однократно.

Итог локальной проверки 29.09.2026: **579/579 тестов**, typecheck, lint, production-сборки A/B, оба Chromium-сценария и документационный checker прошли. Desktop/mobile снимки просмотрены. Последующее read-only ревью не обнаружило новых существенных замечаний.

Проверки браузера с mock API не доказывают готовность production/CDN, качество AI или работу на физических устройствах. Общий статус PWA ведётся в [roadmap, ECO-1](superpowers/plans/roadmap.md).
