# Chronicle Engine v2.2 — надёжные ходы, память и развилки

> Исторический документ этапа. Актуальные статусы и приоритеты на 19.09.2026 — в [roadmap](roadmap.md). Чек-листы и результаты ниже отражают исходный план или проверки того этапа; они не являются отчётом о новом прогоне.

## 1. Что повторно изучено

Отправная точка — работающая v2.1. Сверены README, исходный roadmap `a6f9a55`, предыдущий аудит, schema.ts, turn.ts, embeddings.ts, memory.ts, reducers, compact API, создание/чтение сессий, игровой интерфейс и smoke-скрипты. Базовые 52 теста и production-сборка подтвердили исходное состояние.

Цель неизменна: интерактивная история любого жанра, где AI интерпретирует действие, а сервер валидирует и сохраняет изменения. Режимы `preset/free` и механики `d20/rules-light/narrative` остаются явными. D&D не является общим допущением.

Контракт **gemini-embedding-2** перепроверен по [официальной документации](https://ai.google.dev/gemini-api/docs/embeddings): стабильная модель, отдельные batch requests, задачи в текстовых префиксах, без taskType. Модель не заменялась. Для очереди использован поддерживаемый Drizzle `for("update", { skipLocked: true })`.

## 2. Найденные разрывы и сделанные изменения

| Участок | Проблема v2.1 | Реализация v2.2 |
|---|---|---|
| Приём хода | Конфликт обнаруживался после оплаченной генерации; один requestId не связывался с конкретным payload | Durable turn_requests до AI: expectedTurn, SHA-256 input hash, уникальная активная запись на кампанию, lease/fencing, сохранённые dice |
| Повтор | Восстанавливался неполный ответ, outcome превращался в replay; reload терял requestId | Полный TurnResponse в транзакции хода; только replay-флаг отличается. Клиент сохраняет запрос в sessionStorage и проверяет статус после reload |
| Проверки риска | custom:false обходил серверный бросок и принимал произвольный текст | custom:false разрешён только для точного варианта сцены; оба способа ввода проходят serverCheck своего профиля |
| Snapshot API | Сессия и её таблицы читались вне общей блокировки, могли относиться к разным ходам | Короткая транзакция чтения под session advisory-lock; никаких сетевых AI-вызовов внутри неё |
| Журнал | Игрок/рассказчик могли поменяться местами при одинаковом timestamp | Явный role-order в snapshot, recent context, pagination, export и контрольных точках |
| Semantic extraction | Только after(), без durable job; частичная запись считалась завершённой; пустой результат мог запускаться снова | memory_jobs, lease + SKIP LOCKED, bounded attempts/backoff, все факты + embedding outbox + completed атомарно. Ноль фактов тоже completed |
| Работа без открытой страницы | Нет deployable постоянного обработчика | Один bounded processor для after/manual/CLI; worker с SIGTERM/SIGINT и heartbeat. `/system` не считает файл worker запущенным сервисом |
| Альтернативные пути | Нет снимков истории для независимых веток | Immutable checkpoint всего состояния и истории; stable checksum, remapping UUID/ссылок, отдельная память и outbox в новой кампании |
| Компакция | Обрыв между парой ходов, поштучные записи, незащищённый lastCompactTurn, усечение больших дайджестов | До 6 завершённых narrator turns с соответствующими действиями; сводки с цитатами либо точные bounded fragments; общий commit + CAS указателя |
| Инвентарь в контексте | Нужный предмет мог оказаться за пределами первых 14 | Приоритет полного ID, #ref и точного имени перед квестовыми/экипированными предметами; проверка границ слов и чисел |
| Применение предмета | Неверная ссылка могла тихо перейти к поиску по имени; коллизии коротких ref брали первый предмет | Explicit ref имеет приоритет; неизвестный/неоднозначный ID и неоднозначное имя отклоняются |
| Retrieval | Embedding запроса оплачивался даже при пустом/устаревшем индексе | Сначала проверяется наличие пригодных current model/dims/hash строк, затем вызывается провайдер |
| Входные данные | req.json() с произвольной coercion и доверием Content-Length | Ограниченный потоковый reader, boolean/integer/UUID/requestId validation; raw SQL/provider errors не возвращаются из настроек |

## 3. Реализованный план

- [x] Приём хода до AI: короткая транзакция, одна активная lease, revision, input hash, сохранённый бросок.
- [x] Fencing перед изменением мира и атомарная запись результата для replay.
- [x] Восстановление клиентского запроса после перезагрузки вкладки, стадии работы, явный безопасный повтор.
- [x] Durable semantic jobs и полная атомарность обработки фактов, включая пустой результат.
- [x] Общий processor и отдельный worker CLI; реальные queue/heartbeat метрики и ручной retry.
- [x] Immutable checkpoints, checksum, независимое ветвление без наследования будущего и переиспользования чужих ID.
- [x] Диалог развилок, информация об источнике ветки, сохранение/подтверждаемое удаление точек.
- [x] Согласованное чтение snapshot, стабильная сортировка ходов, безопасная компакция.
- [x] Приоритет используемого инвентаря и отказ от неоднозначных ссылок.
- [x] Unit/integration/browser регрессии, миграции чистой БД и повторный запуск.

## 4. Протокол хода

1. Ограничить размер тела и проверить action/custom/requestId/expectedTurn. Пустое действие и coercion строк в boolean не принимаются.
2. В короткой транзакции заблокировать кампанию, проверить replay и input hash, статус, версию сцены и активную lease. Старую истёкшую lease инвалидировать.
3. Сохранить request, baseTurn, dice, token и срок аренды **90 секунд**. Для повторной попытки того же запроса сохраняется бросок; изменившаяся сцена требует нового решения.
4. Освободить DB-транзакцию. Загрузить контекст; retrieval ограничен 6 секундами, генерация — 30 секундами на цепочку. Выполнить runtime parser/reducers.
5. Под session-lock повторно проверить версию, token, срок и status. Записать игрока, рассказчика, мир, связанные таблицы, state memory, semantic job и полный response одним commit.
6. after() только ускоряет уже сохранённую работу. При ошибке внешнего API свободная кампания не получает процедурную прозу.
7. Browser хранит pending request до отправки, опрашивает status и не пересоздаёт requestId при повторе. После подтверждённого результата запись удаляется.

Гарантия: один commit состояния для принятого запроса и защита от позднего владельца lease. Это **не exactly-once внешней оплаты**: если процесс погиб во время AI-call, провайдер мог уже потратить квоту; после истечения lease повтор иногда потребует нового вызова. Для provider-side exactly-once нужен поддерживаемый самим провайдером idempotency contract.

## 5. Очереди памяти и эксплуатация

### Semantic jobs

- Ключ уникальности: `(sessionId, turnNumber, kind)`.
- Payload — исходная проза, намерение, профиль и известный контекст, без API-ключей.
- `pending → processing → completed`, либо отложенный `pending`, затем `failed` после трёх попыток.
- Lease **60 секунд**; сетевой extraction-call ограничен 15 секундами.
- Попытка учитывается при захвате задания, поэтому падение процесса не обнуляет retry budget.
- Применение фактов проверяет token и срок под блокировкой. Все факты, embedding outbox и completed записываются вместе.
- Ошибочный JSON не считается успешным пустым результатом. Валидный `{facts:[]}` считается завершением.

### Embeddings

Остаётся стабильный `gemini-embedding-2`, 768 по умолчанию, точное совпадение пространства, валидация векторов и content-hash CAS. Ручной reindex проверяет существование кампании и embeddingsEnabled, обрабатывает одну пачку и оставляет остальные задания durable worker. Попытка теперь учитывается уже при claim, а исчерпавшие retry budget истёкшие задания переходят в failed.

### Worker

`node --env-file=.env --import tsx scripts/memory-worker.ts` — длительный процесс, `--once` — один проход. За tick обрабатывается одно semantic-задание и одна пачка до 32 embeddings, далее пауза 15 секунд. Все сетевые вызовы вне транзакций. Несколько workers допустимы благодаря fencing и атомарному claim, но нагрузку/квоты нужно учитывать отдельно.

Экран `/system` показывает сохранённые состояния очереди, действующие turn leases, готовые replay records, число точек, incompatible vector spaces и последние semantic jobs. Online-worker определяется по heartbeat и статусу, а не наличию файла. После `--once` записывается stopped. Статус processing у queue-строки может ждать восстановления истёкшей lease: следующий проход подхватит её.

**В проверочной среде worker запускался только с `--once`, без постоянного процесса.** Для развёртывания нужны systemd/supervisor/контейнерный оркестратор и отдельный мониторинг.

## 6. Контрольные точки: содержимое и гарантии

Снимок сохраняет:

- session character/world/profile/scenario и counters;
- весь журнал до подтверждённого текущего хода;
- inventory, locations, quests, NPC, scene objects;
- memory nodes, parent relationships, memory links;
- summary для UI и число ещё не завершённых extraction jobs на момент снимка.

Не переносит ключи, token logs, worker state, requestId старых ходов, старые turn leases, неполученные факты и векторы. Снимки immutable, checksum строится по канонически отсортированным ключам JSON: PostgreSQL JSONB не ломает проверку порядком свойств.

Fork переназначает session/entity/node/turn/link IDs, UUID в каноническом тексте/keys, однозначные #short refs, world flags, parentId, connectedTo и retrievedIds. Ссылки за границы копируемого набора не наследуются. Новый session active, имеет branchOrigin, свою очередь индексации и не содержит будущего исходной кампании.

Создание точки и fork идемпотентны по requestId, с проверкой назначения запроса. Несовпадение checksum или попытка обратиться к чужому checkpointId даёт ошибку. Удаление точки или исходной кампании не является каскадным удалением уже созданной ветки.

Пределы: 12 точек/кампанию, 4 МиБ/снимок, 2000 journal rows и 1000 строк каждого типа сущностей. Превышение не скрывается усечением.

Это **не восстановление произвольного прошлого**. Точку надо сохранить заранее. Поздний extraction не дописывает её память задним числом. Без encryption/auth снимок не является защищённым внешним backup-файлом: это внутренняя immutable запись приватного пространства.

## 7. Проверки и наблюдаемые результаты

### Unit: 70 тестов

Сохранены 52 проверки v2.1, добавлены сценарии input hash, runtime input validation, streamed body limit, pending recovery parsing, PostgreSQL JSONB checksum order, remapping ID/parent/link/retrieval provenance, запрет будущего/чужих сущностей, Unicode chunking, backoff, приоритет используемого предмета и неоднозначные inventory refs.

Новая регрессия поймала реальный дефект: `Инструмент 2` совпадал как подстрока с `Инструмент 23`. Исправлено сопоставление по границам букв/цифр; тест не ослаблялся.

### Integration: `scripts/v22-smoke.ts`

- Снимок → изменение исходного мира → fork: старое количество предметов, отношение NPC и состояние объекта восстановлены; будущего факта нет.
- UUID, entityKey, parentId и memory links независимы; outbox принадлежит ветке.
- Повтор создания точки/ветки не дублирует сущность; другой payload под тем же ID отклоняется.
- Повреждённая checksum не позволяет создать ветку. Поиск по пустому индексу делает ноль обращений к провайдеру; snapshot во время записи хода остаётся согласованным.
- **Шесть конкурентных действий → один вызов тестового генеративного провайдера**. Полный ответ replay сохранён; неправильная base scene отклоняется до провайдера.
- Выбор готового варианта d20 тоже возвращает серверный бросок: режим ввода не обходит профиль механик.
- Просроченный владелец turn lease не может commit; новый владелец того же запроса получает сохранённый dice.
- Одно semantic job берёт один worker; нулевой результат завершается; факты и outbox появляются атомарно; старый worker не пишет после смены token.
- Повтор компакции не двигает указатель назад/не дублирует итог. История сортируется player/narrator стабильно.
- Offline queue status и отключение provider processing без ключей не имитируют успех.

Базовый `scripts/smoke.ts` также проходит: восемь пресетов, атомарное создание, CAS embeddings, изоляция сессий, archive/restore/export, free AI_REQUIRED.

### Browser: `scripts/v22-browser.ts`

- Сохранение точки, fork, другая версия действий, возврат к оригиналу, lineage и удаление точки без удаления ветки.
- **Потерянный после server commit ответ + reload**: browser заранее сохранил requestId, восстановил уже записанный ход и не отправил новый POST.
- Реальная диагностика, отсутствие ложного online-worker и недоступная без ключа обработка.
- Desktop 1440 и mobile 390: нет горизонтального overflow или page errors. Снимки в `artifacts/v22-*.png`.

Базовый browser smoke также проходит. Clean-DB script проверяет три миграции, новую схему и повторный запуск без добавления ledger entries. Typegen, TypeScript, production build и управляемый runtime healthcheck выполняются финальной последовательностью. `npm audit --omit=dev` показывает 0 advisories на момент проверки.

Тестовый provider явно mock. Настоящего Gemini-ключа в окружении нет; **recall@K, реальная latency/cost и литературное качество не измерялись**.

## 8. Что делать дальше

### P0: приватность и бюджет

1. Verified identity/OIDC, ownerId во всех сущностях, единая авторизация каждого API, затем RLS как второй барьер. Текущая версия — single-owner workspace.
2. Envelope encryption API-ключей через KMS/Vault, key-id, rotation, migration plaintext → ciphertext. Не сохранять master secret рядом с БД.
3. Atomic provider-budget ledger по Google-проекту, не по числу ключей. Резервировать capacity до вызова, учитывать все попытки и real usage. Нынешние daily-count checks ещё не являются атомарными квотами.
4. Request/job retention policy: outcome records, payloads и checkpoints имеют стоимость хранения. Нужны backup/restore drills и политика удаления с учётом конфиденциальности историй.

### P1: масштабирование на измерениях

1. Нагрузочный набор: кампании с 100/1000/10000 nodes, очередь после простоя, 10/100 конкурентных кампаний. Измерить p50/p95 admission/read/retrieval/provider/commit и oldest-pending age.
2. Добавить dispatch/expiry indexes по фактическому query plan; batch inserts/upserts; глобальный provider concurrency cap. Worker уже вынесен, но performance SLA не заявляется без нагрузки.
3. pgvector HNSW для больших сессий с tenant/session фильтрами; `real[]` fallback для маленьких. Версионированные embedding spaces, backfill и контролируемый cutover. Не смешивать Embedding 2/001/preview.
4. Context token accounting и immutable canon cache; targeted SQL retrieval вместо полного cosine scan. Оптимизация не должна выбрасывать явно используемый itemId или квестовый канон.
5. Непрерывная эксплуатация: supervisor, alert на queue age/failed/expired leases, provider cooldown и circuit breaker.

### P2: содержание и качество

1. Размеченный semantic benchmark с hard negatives: recall@5/@8, precision, стоимость и no cross-session leaks. Отдельный eval жанра/тона/противоречий реальной модели, а не только контрактов reducers.
2. Authored scene graphs/story packs вместо общих offline beats; typed quest dependencies, NPC agendas и scene clocks.
3. Отделить подтверждённые факты, гипотезы и реплики NPC. Цитата доказывает наличие источника, но не entailment: нужны versioned facts, contradiction links и явная проверка следования.
4. Event-sourced changes + versioned snapshots для произвольного branch-from-turn. Не выдавать копирование текущего JSON за корректный исторический replay.
5. SSE/Web Streams: статусы и художественный текст до commit, окончательное состояние только после commit. Мультимодальный канон через Gemini Embedding 2 — после pipeline проверки MIME/размеров, provenance и chunking.

## 9. Границы завершённого этапа

Не реализованы публичный multi-tenancy, encryption at rest, атомарные Google-project quotas, pgvector, real model evaluation, произвольный исторический replay, import/export полного внешнего backup или мультимодальный ingestion. Отдельный worker готов к развёртыванию, но не оставлен работающим в фоне песочницы. Изменения не опубликованы в исходный GitHub.
