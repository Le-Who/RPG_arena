# Интеграция четырёх revisions: дизайн и критерии приёмки

Дата: 23 сентября 2026. База исследования: `a423974` и пользовательские изменения roadmap в рабочем дереве.

Статус: состав выборочного переноса одобрен пользователем; пользователь разрешил дорабатывать ранее отклонённые идеи. Уточнение пользователя: аккаунты необязательны, административные поверхности доступны только администрации; рекомендации от 21 сентября рассматриваются выборочно. Реализация и проверки ещё не выполнены.

## 1. Цель и границы

Изучить все четыре поставки, перенести полезные изменения, исправить выявленные дефекты интеграции и обновить документацию, включая оба roadmap. Основание для переноса — полезность функции, совместимость с текущим продуктом и проверяемость её гарантий, а не название версии или заявления авторского отчёта.

Проект остаётся движком универсальных интерактивных историй. Аккаунты и эксплуатационные улучшения поддерживают этот продукт, но не превращают работу в запуск публичного SaaS. Публикация, изменение реальной БД, ротация реальных секретов и вызовы платных провайдеров не входят в локальную интеграцию.

## 2. Результаты сравнения и решения

При сравнении содержимого исключён шум CRLF/LF. Дополнительная побайтовая проверка установила: Astra1 и Astra2 имеют одинаковые 286 файлов.

| Поставка | Полезные идеи | Решение и необходимая доработка |
|---|---|---|
| Astra1 / Astra2 | Обзор, командная палитра, объяснение последствий, шифрование с owner/provider AAD, readiness и очередь | Перенести выборочно; сохранить ресурсы, действующие npm-команды и настройки чтения; проверить доступность и мобильный интерфейс |
| Fable1 | Аккаунты, перенос гостевой истории, структурная валидация импорта | Доработать отзыв гостевого доступа, сессии и конкурентные операции; использовать проверки внешних данных в общем формате импорта |
| Fable2 | Резерв квоты до запроса, переносимый snapshot, Docker/systemd, опциональные startup migrations | Доработать покрытие всех вызовов, идемпотентность импорта, ошибки миграций и воспроизводимость сборки |
| Все варианты | CI и проверки документации | Объединить необходимые проверки; lock-файла в поставках нет, поэтому `npm ci` без его создания неработоспособен |

Не переносить изменения ради совпадения с поставкой: понижение Next.js/PostCSS, перезапись старых миграций, удаление обложек и npm-команд, чужие отчёты как доказательство наших проверок. Три несовместимых формата шифрования заменить одним контрактом, а не поддерживать одновременно без потребности в миграции реально развёрнутых вариантов.

## 3. Общие инварианты

- Сохранить текущие версии зависимостей как нижнюю границу; не заменять целиком `package.json`.
- Сохранить пользовательские изменения `docs/superpowers/plans/roadmap.md` и `docs/development-roadmap-2026-09-20.md`.
- Не изменять поставки в `revisions/`; исключить их из обхода TypeScript, ESLint и артефактов сборки.
- Не изменять миграции `0000–0010`; новые таблицы вводить последовательно после текущего ledger. Разные изменения с номером `0011` из поставок не объединять под одним историческим идентификатором.
- Сохранить ownership, lease/fencing, requestId, проверку expectedTurn, транзакционную фиксацию канона, immutable checkpoints и provenance договорённостей.
- Прочитать локальные руководства Next.js перед изменением соответствующего кода.
- Проверять работу на изолированной тестовой БД, без выполнения миграций или ротации против пользовательской `.env` по умолчанию.

## 4. Секреты и аккаунты

### 4.1. Один механизм хранения секретов

Использовать основу Astra: AES-256-GCM со случайным IV, явным идентификатором ключа и AAD, включающим владельца и назначение секрета. Master key принимается только как корректный 32-байтовый ключ; произвольные парольные фразы и тихий возврат plaintext не допускаются. Сохраняемые секреты Gemini, пилота Jev и narrative verifier проходят один серверный слой.

При отсутствии ключа разрешены пустые настройки и игра без AI; запись непустого секрета возвращает понятную ошибку. Чтение старого plaintext разрешается только отдельным явным флагом переходного периода. Ошибка расшифрования не превращается в пустой секрет и не приводит к его перезаписи. API возвращает только маскированные представления.

CLI ротации получает dry-run/check режим и обновляет секреты без потери конкурентных изменений. Реальная ротация запускается отдельно оператором. Документация описывает порядок включения, сохранение старого keyring на период миграции и ограничения защиты резервных копий.

### 4.2. Аккаунты без обхода через гостевую cookie

Использовать идеи Fable1: логин, scrypt-хеш пароля, случайные session tokens, только их хеши в БД, выход, выход со всех устройств и смена пароля. При регистрации существующий профиль закрепляется за аккаунтом транзакционно: сервер больше не допускает доступ к закреплённому profileId по гостевой cookie, даже если она сохранена в другом браузере. Простого удаления cookie на клиенте недостаточно.

Гостевой доступ остаётся полноценным: без регистрации можно создавать и продолжать свои кампании, пользоваться личной памятью, настройками BYOK и экспортом. Интерфейс объясняет, что потеря гостевой cookie может лишить доступа к историям, а аккаунт позволяет входить с другого устройства.

При регистрации кампании текущего гостя становятся кампаниями аккаунта. Физически профиль может сохранить ID; обязательно меняется серверное основание доступа. Старый гостевой токен больше не открывает этот профиль. Браузеру выдаётся новый гостевой токен, поэтому первый выход из созданного аккаунта открывает пустое гостевое пространство.

Повторный вход в существующий аккаунт не переносит новые гостевые кампании автоматически. После входа показывается предложение переноса с количеством кампаний и отдельным подтверждением. Отказ оставляет их в гостевом пространстве этого браузера; выход возвращает к нему. Если перенос подтверждён, кампании передаются аккаунту транзакционно, гостевой профиль помечается переданным и его токен больше не даёт доступ к переданным данным; браузер получает новый пустой гостевой профиль. Такая же защита применяется к старой cookie в другом окне. Нельзя разрешать повторный перенос от другого аккаунта.

Все маршруты разрешают владельца через единый resolver. Повтор регистрации одного профиля и перенос гостевых кампаний сериализуются с проверкой ownership внутри транзакции. Перенос между разными ownerId учитывает AAD: секреты не копируются как ciphertext между владельцами. Перенос кампаний не означает автоматического объединения AI-ключей. В интерфейсе до подтверждения объясняется, что личные настройки и ключи гостя не заменят настройки существующего аккаунта. Фоновые работы после смены владельца повторно проверяют актуального владельца перед использованием настроек и фиксацией результата.

Отзыв сессий должен действовать во всех процессах, без положительного локального кэша, продолжающего разрешать отозванный токен. Изменяющие auth-запросы проходят проверку происхождения. Лимит попыток хранится в БД; смена логина в запросе не обходит общий лимит регистрации, а заголовки прокси не считаются доверенными без явной конфигурации. Ошибки входа не раскрывают наличие аккаунта. UI честно указывает отсутствие самостоятельного восстановления забытого пароля; recovery/email/passkeys не объявляются реализованными.

Приёмка: игра гостем без регистрации; регистрация сохраняет кампании; вход со второго устройства работает; старая guest cookie без сессии не открывает аккаунт; первый выход после регистрации открывает пустого гостя; новые гостевые кампании не перемещаются при входе без подтверждения и доступны после выхода; явный перенос работает однократно; logout/logout-all/password change отзывают нужные сессии; чужие кампании недоступны; конкурентная регистрация не создаёт двух владельцев одного профиля.

### 4.3. Административная роль не равна владению кампанией

Администратор — аутентифицированный аккаунт, ID которого указан в серверном allowlist `CHRONICLE_ADMIN_ACCOUNT_IDS`. Пустой список запрещает доступ всем. Саморегистрация, имя пользователя, номер первого аккаунта, profileId из запроса и клиентский флаг не назначают роль. Назначение и отзыв выполняются оператором через конфигурацию сервера; роль проверяется на каждом серверном входе в административную функцию. После изменения окружения перезапускаются все экземпляры приложения и worker; это ограничение конфигурационного allowlist документируется.

| Поверхность | Доступ | Серверное правило |
|---|---|---|
| `/system`, API `/api/system/status`, `/api/system/process` | Только администрация | Проверка роли до чтения диагностики и запуска обработки; текущая область владельца не расширяется автоматически |
| Раздел «Для разработки», `/api/developer/typesafe`, `/test`, `/results` | Только администрация | Проверка роли до получения ключей, результатов или внешнего запроса |
| `/api/sessions/:id/narrative-diagnostics` | Только администрация и владелец кампании | Технический журнал не выдаётся обычному игроку; роль не отменяет ownership |
| `/memory`, журнал, персонажи, кампании, личные настройки, BYOK, статистика собственных затрат | Гость и аккаунт | Существующие проверки текущего владельца; без глобального heartbeat и технических сведений о БД |
| Поиск и переиндексация собственной памяти, компакция, экспорт | Владелец | Сохранить ограничения размера, квоты и предупреждения о расходе; не переводить личные функции в admin-only без причины |
| `/blueprint` | Публичная справочная страница | Актуальное описание возможностей, без runtime-диагностики, ключей и административных команд |
| `/api/health` | Публичный минимальный readiness | Только безопасный статус готовности; подробная диагностика доступна администрации |

Административная страница возвращает 404 для недопущенного посетителя, API — 403. Скрытие меню, карточек и командной палитры дополняет, но не заменяет серверный запрет. Проверить прямые URL, альтернативные методы запросов и старые сохранённые настройки. Worker не запускает экспериментальный Jev memory pilot для неадминистратора даже при ранее сохранённом enabled=true; narrative verification игрового хода — отдельная функция и не выключается этим правилом.

Обычный пользователь получает личные показатели готовности памяти без инфраструктурных деталей. Администратор не получает автоматически право читать тексты чужих историй, менять их ключи или играть от чужого имени. Глобальная управляющая панель и операции над чужими очередями требуют отдельного целевого контракта и не появляются как побочный эффект role guard.

Приёмка: матрица guest/account/admin; прямой обход UI; пустой allowlist; отзыв разрешения после обновления конфигурации; запрет до side effect; отсутствие вызова Jev из worker для недопущенного владельца; сохранение гостевых и личных игровых возможностей.

## 5. Квоты

Основа — отдельный атомарный резерв Fable2 перед каждой фактической попыткой обращения к провайдеру, включая повтор и fallback. Это локальный лимит приложения, не обещание точного совпадения с биллингом провайдера. Граница суток задаётся явно; неверный timezone отклоняется вместо тихой подмены.

Проверить все пути Gemini: основной ход, adjudication/repair, создание истории, извлечение памяти, компакция и эмбеддинги. Для разных API/единиц квоты определить отдельные области счётчика; не объявлять общий контроль реализованным, если путь обходит резерв. Несколько ключей по умолчанию не умножают лимит одного проекта; независимость квот требует явной настройки.

При исчерпании лимита запрос к провайдеру не отправляется. Неопределённый сетевой результат не освобождает резерв автоматически. При включении новой схемы учесть текущий расход, чтобы обновление не предоставляло повторный дневной бюджет. Семантика пользовательского отключения enforceLimits сохраняется и документируется.

Приёмка: конкурентные запросы не превышают установленный cap; лимит применяется перед fetch; повтор и fallback резервируются отдельно; границы суток корректны; исчерпание не повреждает канон кампании.

## 6. Переносимые кампании

Использовать один versioned JSON-контракт с форматом, версией, временем экспорта, checksum и snapshot. Checksum выявляет повреждение, но не удостоверяет автора и не заменяет валидацию. Объединить структурные проверки Fable1 и snapshot/provenance проверки текущего проекта, сохранив архитектуру переиспользуемого snapshot из Fable2.

Проверять типы каждой строки, допустимые значения, числовые диапазоны, даты, размеры, уникальность и ссылки до записи. Не вставлять произвольные пользовательские поля через слепой spread. Импорт создаёт приватную кампанию с новыми ID, не переносит ключи, billing, задания, leases и requestId ходов. Эмбеддинги ставятся в outbox без внешнего вызова.

Idempotency key привязан к владельцу и запросу. Повтор того же документа возвращает результат; другой документ с тем же ключом возвращает конфликт. Параллельные повторы не создают дубликаты и не заканчиваются необработанным unique violation. Экспорт использует согласованный снимок при конкурентном ходе. Полный JSON-экспорт доступен владельцу, пока для публичного snapshot не определён отдельный reveal/redaction контракт.

Приёмка: round-trip состояния и договорённостей, remap связей, отклонение повреждённого и чужого snapshot, размеры и версии, конкурентные повторы, rollback без частичного импорта.

## 7. Интерфейс

Уточнение пользователя: отдельно проверить представление модальных окон. Они не должны выглядеть как страница, обрезанная ограниченным viewport. Для настроек, создания истории, контрольных точек, карты, командной палитры, справки и обновлений нужны подходящий задаче размер, собственная компактная шапка и доступные действия, одна осмысленная область прокрутки без дублирования page chrome. Проверить длинный контент, увеличенный текст, desktop и мобильный экран, затем исправить обнаруженные проблемы компоновки. Сохранить фокус, Escape, блокировку фоновой прокрутки и возврат к незавершённой форме при вложенных диалогах.

Перенести обзор Astra, командную палитру, поиск/фильтры/избранное и подробности применённых последствий. Сохранить текущие локальные обложки, настройку чтения, sepia/high contrast/reduced motion, мобильную навигацию и восстановление хода. Локальные данные избранного и недавних команд не должны смешивать пространства разных аккаунтов.

Встроить UI аккаунтов и JSON-переноса без потери существующего Markdown-экспорта. Команды контекста кампании учитывают права и состояние запроса; открытие диалогов не теряет несохранённый ввод. Последствия ссылаются на реально существующий committed turn.

Приёмка: браузерные сценарии создания, продолжения, checkpoint, импорта/экспорта, входа/выхода; клавиатура и фокус; мобильный viewport; отсутствие ложных заявлений об автономной работе браузера без сервера.

## 8. Эксплуатация

Расширить readiness проверками необходимой схемы и возможностей поиска; диагностику очередей — возрастом pending, heartbeat и явно обозначенной долей failed в текущем снимке, а не мнимой оконной метрикой.

Сохранить отдельный шаг миграций как основной способ деплоя. Опциональный startup режим по явному флагу использует существующий transactional advisory lock. Ошибка пробрасывается и блокирует готовность приложения; процесс не объявляется успешно запущенным на неполной схеме. Проверить поведение web и worker отдельно.

Адаптировать Docker/systemd и CI к этому репозиторию: действующие npm-команды, воспроизводимый lock-файл, исключение `.env`, `revisions`, локальных артефактов и секретов из образа. Не устанавливать и не запускать службы на компьютере пользователя. CI включает typecheck, lint, тесты, проверку документов, миграции с повтором и production build.

## 9. Порядок независимых этапов

1. Воспроизводимость baseline, учёт источников и сохранение пользовательских изменений.
2. Единое шифрование и безопасный переход со старого формата хранения.
3. Необязательные аккаунты, перенос гостевых кампаний, административные границы и отзыв гостевого доступа поверх единого хранения секретов.
4. Квоты с конкурентными тестами и аудитом всех внешних вызовов.
5. Переносимость кампаний с транзакционными и негативными тестами.
6. UI и браузерная проверка взаимосвязанных сценариев.
7. Readiness, deployment, CI и итоговая актуализация документации.

Для этапов реализации составляются отдельные проверяемые задания; незавершённая часть не выдаётся за весь релиз. Перенос функций не означает автоматического принятия всех утверждений документации поставки.

Обновить `/blueprint`, подсказки настроек, описание гостевого доступа, обновления и версии в UI по фактически реализованному состоянию. Исторические результаты оценок не переписывать как новые измерения.

Завершение требует актуальных результатов typecheck, lint, полного набора тестов, build, проверки ссылок/команд документации, миграций на изолированной БД и браузерных сценариев. Отдельно зафиксировать непроведённые live AI, нагрузочные и внешние deployment-проверки. Наличие файлов и зелёные узкие unit-тесты сами по себе не доказывают безопасность аккаунтов, атомарность квот или полный round-trip кампании.

## 11. Оценка приложенных рекомендаций от 21 сентября

Источник: предоставленный пользователем `rpg_arena_implementation_plan_ru.md`, ссылающийся на commit `a423974`. Рассмотрен как рекомендации, а не команды к исполнению. Упомянутый в нём «пакет из этой папки» не приложен и не считается установленным или проверенным.

- **Включить в текущую интеграцию:** серверный admin guard, разделение роли и ownership, защита прямых Jev API и фонового пилота, личные показатели вместо инфраструктурной диагностики для обычного пользователя, сохранение fencing и owner-specific credentials, проверка квот до внешнего вызова, актуализация `/blueprint` и документации.
- **Включить в эксплуатационные улучшения:** отдельный lifecycle worker, конфигурация ограничений ресурсов, уникальные heartbeat по worker instance вместо одного общего `memory:worker`; наличие deployment-конфига не считать доказательством запущенного сервиса. Проверить, что остановка одного instance не помечает остальные остановленными.
- **Зафиксировать следующим отдельным этапом roadmap:** справедливый планировщик по владельцам, независимые пулы extraction/embedding, измерение ожидания БД и отставания, ограниченные backfill после смены dims/включения extraction. Эти изменения требуют самостоятельных нагрузочных и стоимостных критериев; автоматического платного backfill без согласия владельца не вводить.
- **Оставить исследовательским этапом:** типизированные графовые связи и иерархические summary, отдельный held-out корпус длинных историй, сравнение качества retrieval при фиксированном бюджете. Существующие provenance и проверки области кампании сохранить.
- **Не внедрять без измерений:** ANN, PQ/ADC, смену embedding-модели или векторного расширения. Предоставленный документ не доказывает их необходимость для этой интеграции; exact search остаётся эталоном. Ссылки и численные технические утверждения документа требуют проверки первоисточников, если соответствующий этап будет начат.
