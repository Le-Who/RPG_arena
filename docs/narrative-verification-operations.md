# Selective narrative verification

The default-enabled turn guard resolves game mechanics once, then verifies consequential narration against the accepted result and independently retrieved original turns. It can repair narration and choices once, verifies the repair, and commits only the final version. The same version feeds history, chapter memory and semantic extraction. Dice and reducer operations are never recalculated during repair.

## Configuration and rollout

Migration `0007_narrative_verification` adds separate owner-scoped settings, enabled by default in this unshipped feature migration. The existing deployment migration runner applies it before building. No production migration or deployment was performed during this development work.

Migration `0009_narrative_evidence_search` adds a stored Russian full-text vector and GIN index for original turns. The query ranks indexed matches plus explicit source references and recent turns, then fetches only the selected turn texts. PostgreSQL computes the vector for existing rows and updates it automatically on edits; it is excluded from ORM/client/copy payloads. Adding the stored column rewrites existing rows and takes a table lock during migration, so deploy duration depends on total history size. The migration runner's existing timeout/transaction rollback applies; do not treat local fixture timings as a production migration-time estimate.

The same PGlite fixture with 100/1,000/10,000 turns (two rows per turn) found the original contract by lexical search and by explicit reference, excluded foreign/future rows, and respected 40-row/32k-text bounds. Before this change, the 10,000-turn queries took 6.3–8.9 seconds; after it, repeated local runs took 33–194 ms. These are synthetic local database measurements, not end-to-end provider or Neon latency guarantees.

In Settings → «Проверка повествования», choose OpenRouter or TypeSafe, save that provider's key, and enable verification. Changing the provider removes the old credential. These settings are separate from the diagnostic memory pilot and from Gemini credentials. Gemini and pilot keys remain personal. Jev alone has an explicitly authorized server fallback: `NARRATIVE_ADMIN_OPENROUTER_API_KEY`, or `NARRATIVE_ADMIN_TYPESAFE_API_KEY` when the former is absent. A valid personal Jev key takes precedence; an explicit personal opt-out is respected. The shared credential and even its suffix are never included in the settings response. Ordinary evaluation variables do not implicitly enable shared production billing.

Without either Jev credential, the turn follows the legacy unchecked path. If a configured Jev returns unavailable (including transport error, timeout, malformed response or quota failure), the turn continues unchecked and records the reason. An explicit contradiction or uncertainty is not an outage; normal repair/review rules still apply. Invalid generation, expired lease and an unverified repair without a Jev outage still prevent commit. The existing request ledger preserves idempotency and dice on retry. The UI displays «Сверяем рассказ с событиями». There is no automatic retry loop or Gemini substitution for unavailable Jev. On bypass, unverified provisional independent inventory gains and new agreement revisions are not admitted; the last draft checked is used, never an earlier rejected version.

An uncertain Jev answer now triggers a bounded second review by the player's configured narration model, using the same frozen state and current draft. This is disclosed in settings and consumes that player's Gemini quota. It cannot override a confident Jev rejection and is never invoked for verifier unavailability; unavailable Jev follows the explicit unchecked bypass above. Each draft allows at most one review (6-second deadline); a turn still allows at most one prose repair. Review output must cover the exact question IDs and cite matching source values. Invalid output or expiry stops the turn. The audit retains Jev responses and separate `reviews` with attempt, model, timing and evidence. Only approval for the final checked draft and matching saved-text hash can establish verified historical authority.

For historical contradiction verdicts, a request, legacy/disputed narration, future source or current candidate alone is insufficient: the parser downgrades that verdict to uncertainty and preserves `reportedVerdict`. Independent-acquisition approval additionally requires a reference to pre-turn state or confirmed history. These source checks do not prove semantic entailment; the reviewer still evaluates whether the cited facts support the claim.

The reviewer supplies JSON Pointer paths; the server resolves their exact values from the frozen snapshot. This avoids model errors while copying large JSON objects. Older quoted responses remain acceptable only when the supplied quote matches. Distinct citations have a 32k-character budget; each reference is limited to 8k, except `/draft` which supports the existing 12k draft limit. Repeated references to the same path/value count once. These are coverage limits, not silent truncation.

The first live integrated guard run with generated quotes approved only 1/3 valid cases: two calls timed out at six seconds and one response omitted fields while quoting an object. After switching to server-resolved paths, a new five-case run approved 3/3 valid cases (2,526–3,461 ms), rejected the failed-goal acquisition without a second reviewer (458 ms), and sent the forged district contract to repair (3,435 ms; repair deliberately disabled in this harness). This is synthetic admission testing on captured performTurn inputs, not production latency or a full generation/repair benchmark. `scripts/eval-narrative-pipeline.ts` retains sanitized attempt diagnostics and synthetic responses for reproducibility.

## Streaming and evidence

Guarded generation puts metadata before narration. Only complete descriptive sentences may stream early after conservative admission. Dice, proposed or automatic effects, historical references and consequential choices cause buffering. A later escalation holds unseen text; repair must preserve any emitted prefix. This selective route is deliberately fallible and does not guarantee detection of every consequential paraphrase.

Each verifier call now omits the choices question for an explicitly empty choices array and the journal question for an explicitly empty accepted agreement array. Missing or malformed fields retain their check. Scope is recalculated after repair; historical assertions and unlisted events remain checked. Audit `checkSelections` records the exact questions for each response, including questions reintroduced by repaired choices.

Historical retrieval is session-scoped and excludes the pending/future turn. It retrieves original player and narrator text, including older turns, with bounded coverage. Persisted audit snapshots contain source IDs, turn numbers, exact excerpts, full-text hashes, clipping markers, source authority, verifier answers and timings. They are not reconstructed later from mutable memory summaries.

Player intentions and summaries do not establish events. Old unverified prose or prose with rejected consequences cannot independently prove material history. Previously verified narration is recognized only when its stored hash still matches the text. An NPC's claim is still a claim. Missing historical support is unknown, not proof of falsehood. Existing campaign history is not automatically corrected or certified by this feature.

Audit: narrator `game_turns.context_meta.narrativeVerification`; elapsed checking/repair time: `timings.verificationMs`. Audit does not include API keys. A failed guard returns a safe `narrative:<reason>` detail; provider error bodies are suppressed. Retained dialogue excerpts are private campaign data and follow campaign ownership.

## Validation and limits

See `narrative-verification-evaluation-2026-09-20.md` and `narrative-heldout-evaluation-2026-09-20.md`. Small synthetic samples showed substantial variation in valid-case abstention. Strict thresholds were retained; unanimity is research-only. Added authority/accepted-note questions require continued evaluation on actual serialized state.

One synthetic live pants repair completed in 2,177 ms: initial Jev rejection 727 ms, Gemini repair 1,076 ms, final Jev approval 371 ms. This excludes the initial narration generation and database commit. It is a single observation, not an end-to-end percentile or measured repair rate.

The feature includes conservative no-roll observation handling and same-turn item acquisition/equipment identity consistency. Failed checks reject acquisition by default. Under enabled live verification only, an explicitly independent addition may be staged provisionally. Every candidate, including stack increases, requires a separate high-confidence independence verdict based exclusively on pre-turn state and confirmed history. The draft and proposed operations cannot establish that basis, and prose repair cannot rescue a failed independence check. Disabled and offline flows retain the default rejection. An offline preset under enabled verification renders accepted consequences deterministically without requiring Jev.

Migration `0008_agreement_events` stores immutable, source-bound agreement revisions with parties, object, consideration, conditions and status. Revisions commit in the same transaction as their narrator source. Checkpoints and personal copies remap identifiers while retaining exact source text and hashes; Markdown exports include the complete journal. Old snapshots without a journal remain readable. Live context and snapshots currently permit at most 1,000 revisions and explicitly fail beyond that limit rather than silently dropping old terms. Verifier requests have a separate 100,000-character cap; long context can reach it earlier. Export does not use the prompt history cap.

The first six-case `eval-narrative-independence.ts` live probe rejected both failed-goal acquisitions, abstained on three unsupported cases, and also abstained on the one supported independent delivery (consistent probability 0.73, confidence 0.59). Replacing generic prose criteria with explicit operation criteria then admitted that delivery. A separate eight-case set admitted all three supported independent acquisitions, rejected both contradictions and abstained on three unsupported cases. That question wording is now used at runtime with unchanged thresholds. These are isolated predicate results, not full-turn reliability: in a subsequent twelve-question batch the independence predicate still passed all three supported cases, but other questions caused overall abstention. Empty/absent-scope questions and full-turn serialized-state calibration remain open.

`eval-narrative-agreements.ts` checks eight synthetic typed-journal scenarios. The current broad agreement question approved one of four valid cases and approved none of four invalid cases. A research-only `--candidate` with explicit record-field criteria still approved only one of four valid cases; it was not promoted. No production data was used. These measurements identify a usability issue before rollout, not evidence of a production-ready semantic gate.

A research-only `--atomic` version also approved only one of four valid agreement cases, so it was not promoted. More representative evidence comes from `eval-narrative-serialized.ts`: it replays the exact state and question sets captured from synthetic PGlite `performTurn` integration scenarios. The first five-call run abstained on all three valid cases, rejected an acquisition that achieved a failed goal, and abstained on the forged district contract. The two invalid cases were not approved, but valid acceptance was 0/3. This is an unresolved release limitation; isolated-predicate successes cannot be used to claim full-turn readiness. To reproduce fixture capture, set `CAPTURE_NARRATIVE_FIXTURES=1` while running `tests/narrative-turn-integration.test.ts`, then run the evaluation script with `--live` and a local OpenRouter key. Capture writes synthetic state and question sets only, never provider credentials.

Research escalation: `eval-narrative-adjudication.ts` evaluates Gemini 3.5 Flash Lite as a possible second opinion for uncertain Jev results. These measurements preceded the bounded runtime integration described above. After correcting ambiguous citation-root instructions, the five serialized scenarios produced three valid approvals, one contradiction rejection and one malformed question ID (rejected by parsing), at 2,566–3,501 ms per call. A separate five-case subset from the earlier held-out corpus approved 2/2 valid and rejected 2/2 contradictory cases, but incorrectly classified one insufficient-evidence case as contradiction. Those cases were new to this Gemini comparison, not a new independently authored corpus. The first version also produced invalid citations and one 16,426 ms response. Do not use the small corrected sample as a latency guarantee. A strict reusable parser now rejects missing/duplicate IDs, fabricated references, mismatched quoted values and malformed output; matching a citation still does not prove entailment. The current parser normalizes unsupported historical contradiction to uncertainty; replay of that saved five-case report now preserves both correct approvals and rejections while returning uncertainty for the request-only case. Broader live evaluation of the complete integrated path is still required.

Development validation includes PGlite-backed `performTurn` tests for repair, canonical persistence, idempotency, provider failure, owner credentials, malformed JSON, failed dice, fast streaming and late escalation. Browser checks used mocked APIs, not a production account. Deployment and public rollout require a separate instruction.


## Attempt diagnostics

`narrative_attempts` (migration 0010) stores each lease attempt separately from committed story facts. It records personal/administrator/no credential source (never the key), policy version, skip/check/bypass/block reason, selected questions and model results, immutable checked state and retrieved source snapshots, original/final candidate text, accepted changes, dice, available token/cost usage and phase timings. Both failed and successful attempts remain inspectable; retries do not overwrite earlier attempts. The final outcome is distinct from the verification decision. A process killed before finalization can leave a running diagnostic record; the authoritative turn request/lease must then be consulted.

Owner-only read endpoint: `GET /api/sessions/{id}/narrative-diagnostics` (requires an allowlisted administrator account AND campaign ownership), optionally `?before={attempt-id}`. Twenty records per page, no cache; public campaign access does not grant diagnostic access. Records never serve as canonical evidence and are not copied into public campaign copies.

Payload details are bounded to 256 KB per attempt snapshot, 12k characters per string, 100 array entries and depth 14, with cumulative truncation markers. Available excerpts and hashes support investigation; omitted detail is not represented as complete evidence. The assembled snapshot is serialized once in the background. No provider headers, raw provider errors, configuration objects or credentials are persisted. Generation token totals include review/repair; Jev responses retain their separately reported usage. Unknown billing cost is not estimated as zero.

Reads expose the most recent 30 days. Batches of at most 100 older records are removed by post-response cleanup as traffic occurs; this is opportunistic cleanup, not a guarantee of physical erasure at the exact 30-day boundary. Campaign deletion cascades immediately. During a turn, diagnostic fields are collected in memory. A single Next.js `after` callback persists the assembled snapshot and final outcome, then prunes expired records, after the response completes (including streamed responses). No diagnostic SQL or serialization is awaited by gameplay. CPU bookkeeping still has a small nonzero cost. Background writes retain 500 ms acquisition/statement/client deadlines; cleanup has a separate 1-second bound. Logging failure emits a fixed safe warning and does not alter the game result. A process terminated before the callback completes can lose the diagnostic attempt; this is observational best-effort telemetry, not a durable gameplay ledger.

The admin fallback and no-check outage behavior were explicitly requested after the initial completion audit; they supersede that audit's opt-in/fail-closed operational policy. Migration 0007 has not been deployed as part of this feature and its initial default was changed to true; no previously deployed migration ledger was rewritten. Existing explicit user opt-outs are not bulk-reset.
