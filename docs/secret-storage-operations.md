# Хранение и ротация API-ключей

Документ относится к интеграции revisions от 23 сентября 2026. Локальная реализация не означает, что реальные credentials уже зашифрованы: ротация пользовательской БД автоматически не выполняется.

## Контракт

Секреты Gemini, TypeSafe memory pilot и проверки повествования хранятся в существующей таблице `ai_settings`. Непустые новые значения шифруются AES-256-GCM со случайным IV. Контекст аутентификации включает ID владельца и назначение ключа; ciphertext другого профиля или провайдера нельзя просто переставить в строку.

Master keys не хранятся в БД. Сервер получает:

- `CHRONICLE_SECRET_KEYS`: JSON-объект идентификаторов ключей и их base64-значений. Каждое значение — ровно 32 случайных байта, закодированных стандартным base64.
- `CHRONICLE_SECRET_ACTIVE_KEY`: идентификатор из этого объекта, используемый для новых записей.
- `CHRONICLE_ALLOW_LEGACY_PLAINTEXT=true`: необязательный временный режим чтения старых незашифрованных credentials. Он не разрешает запись новых plaintext credentials.

Web и worker должны использовать одинаковый keyring. Храните его в секрет-хранилище окружения; не коммитьте `.env`, не добавляйте значения в логи, скриншоты, issue или документацию. Не используйте произвольную парольную фразу вместо случайного 256-битного ключа.

Пустые настройки и игра без AI не требуют master key. Запись непустого API-ключа без корректного keyring запрещается. Повреждённое или нерасшифровываемое значение вызывает явную ошибку, а не превращается в пустую строку. Для таких случаев сначала восстановите нужный keyring или проведите контролируемое восстановление настроек; не пытайтесь «починить» данные слепой ротацией.

## Переход существующей установки

1. Сделайте проверенную резервную копию БД и сохраните keyring отдельно от неё. Определите окно изменения и возможность возврата версии приложения.
2. Настройте первый случайный master key и его активный ID во всех процессах. Если старые credentials ещё нужны до ротации, явно включите временное legacy-чтение.
3. Проверьте целевой `DATABASE_URL` на машине оператора. Следующие команды загружают локальный `.env` согласно npm-script: не запускайте их, пока не проверили целевую БД.
4. Выполните только чтение:

   ```sh
   npm run rotate:secrets -- --check --allow-plaintext
   npm run rotate:secrets -- --dry-run --allow-plaintext
   ```

5. Изучите численные результаты. Ни dry-run, ни check не шифруют БД. Для записи требуется отдельная явная команда:

   ```sh
   npm run rotate:secrets -- --apply --allow-plaintext
   npm run rotate:secrets -- --check
   ```

6. Убедитесь, что `plaintext` и `needsRotation` равны нулю, затем выключите `CHRONICLE_ALLOW_LEGACY_PLAINTEXT` во всех процессах. Проверьте чтение и сохранение настроек, web и worker.

Обработка идёт ограниченными пакетами; запись сравнивает исходные raw-поля с текущими. Если другой запрос изменил credentials/provider, обработка останавливается вместо перезаписи нового значения. Повторите проверку и прогон после выяснения причины. Это не одна транзакция всей БД: уже успешно обработанные профили остаются зашифрованными при остановке более позднего пакета.

## Последующая смена master key

Добавьте новый ключ в keyring, оставив старые, назначьте новый активным и обновите все процессы. Проведите dry-run, apply и check, как выше; для уже зашифрованной БД `--allow-plaintext` не нужен. Старые ключи удаляйте только после отсутствия потребности в ротации и проверки всех процессов.

Резервные копии до ротации могут требовать старый keyring. Старые dump/WAL могут содержать plaintext, если он когда-либо сохранялся: текущая ротация не переписывает архивы. Процедура backup/retention и отзыв API-ключей у провайдера при подозрении на утечку — отдельные действия оператора.

## Диагностика и ограничения

- `SECRET_STORAGE_UNAVAILABLE`: нет корректной конфигурации записи.
- `SECRET_MIGRATION_REQUIRED`: найден legacy plaintext без явного разрешения чтения.
- `SECRET_DECRYPTION_FAILED`: ciphertext нельзя открыть данным keyring/context; не перезаписывать его автоматически.
- Скрипт возвращает безопасные счётчики и ненулевой exit code при ошибке. Для готовности оцените не только exit code, но и `plaintext`/`needsRotation`.
- Settings API выдаёт маски и признаки конфигурации, не исходные credentials.
- Шифрование защищает отдельный дамп БД, но не скомпрометированный работающий сервер, обладающий keyring. Это не KMS и не доказательство готовности публичного сервиса.
