# Chronicle Engine v2.7 — жизнь мира, контекстные действия и визуализация (INTERACT-1/2/3, NARR-7, VIS-1/2)

> Этап от 24.09.2026, контракт Pollinations уточнён 26.09.2026. Описывает фактическое поведение кода; реальные прогоны на провайдерах (Gemini, Pollinations) не проводились и не заявляются.

## 1. Где хранится состояние

Универсальное состояние жизни мира хранится в `game_sessions.world_state` (jsonb) в необязательных полях:

| Поле | Тип | Назначение |
|---|---|---|
| `clock` | `{ day, minute }` | Время мира. Ход не равен фиксированному часу: длительность предлагает модель (`stateChanges.time.advanceMinutes`), иначе сервер берёт значение по типу действия. |
| `story` | `StoryShape` | NARR-7: `scene` / `open-life` / `arc`, для арки — цель, ставки, конфликт, условие завершения; статус `ongoing/resolved`, эпилог. |
| `commitments` | `Commitment[]` | Встречи, обещания, сделки: `proposed → accepted → fulfilled/broken/cancelled`, стороны, место, срок. |
| `holdings` | `Holding[]` | Вещи героя, которые сейчас у NPC или оставлены в месте. |

Почему jsonb, а не новые таблицы: поля автоматически проходят через checkpoints, forks, копирование кампаний и JSON-перенос без изменения этих подсистем. Старые кампании читаются через `readLife()` с безопасными значениями (день 1, 09:00; арка, если есть главная цель, иначе открытая жизнь). Ограничения размера: до 40 обязательств (16 открытых) и 60 записей владения.

Модуль: `src/lib/world-life.ts` (чистые функции, без БД).

## 2. Порядок обработки хода

1. **До AI.** `inferInteraction()` разбирает текст действия (и привязанные `itemIds`) в контракт `{ verb, target, recipient?, minutes? }`; `checkInteraction()` проверяет владение предметом, присутствие NPC в текущем месте, связность мест на карте, состояние объекта. `classifyIntent()` определяет тип высказывания: `act`, `intend`, `claim`, `ask`.
2. **Промпт.** `buildLifePromptBlock()` добавляет форму истории, время, открытые договорённости, «вещи не у героя», тип высказывания и серверно проверенное действие. При невозможном действии модель получает жёсткое ограничение, а не разрешение.
3. **Ответ модели.** Схема `RESOLUTION_RESPONSE_SCHEMA` (и производная guarded-схема) дополнена необязательными `stateChanges.time`, `commitments`, `transfers`, `story`. Парсер `parseLifeChanges()` ограничивает значения.
4. **Фильтр по намерению.** `gateByIntent()` до reducers: утверждение игрока (`claim`) не может завершить цель; вопрос (`ask`) не перемещает и не тратит предметы.
5. **Reducers.** Сначала существующий `applyResolution()`, затем `applyLife()`:
   - передача предмета выполняется только при `accepted=true`, существующем предмете, живом получателе или текущем месте; не для `intend/ask`; не для предмета, уже изменённого в этом ходе; количество проверяется;
   - `accepted/fulfilled` для договорённости при `claim/intend` понижается до `proposed` (INTERACT-3);
   - предмет, вернувшийся герою (`op add` с тем же именем), снимает запись владения;
   - все подтверждённые изменения пишутся в каноническую память (`source=state`) через существующий механизм событий.
6. **Главы.** Граница главы определяется формой истории: арка — при завершении главной цели или подтверждённом условии завершения (не по утверждению игрока); открытая жизнь — при смене дня; сцена — без глав. Прежняя граница «каждые 12 ходов» оставлена только как совместимое значение для незавершённой арки без события.
7. **Офлайн-пресет.** Проверенный переход (`move`) исполняется детерминированно тем же контрактом; время продвигается по умолчаниям действия.

## 3. Контекстные действия (INTERACT-1)

`src/lib/interactions.ts` используется и в UI, и на сервере. Глаголы: осмотреть, взять, использовать, передать, открыть, поговорить, договориться, отправиться, подождать. Кнопка в интерфейсе формирует каноническую фразу (`interactionText`), которая подставляется в поле действия — игрок может её дополнить. Сервер разбирает любую фразу тем же парсером, поэтому кнопка не является отдельным привилегированным API и не обходит admission, requestId и expectedTurn.

Интерфейс: меню «Действия» у вещей, персонажей, объектов окружения, мест карты и оставленных вещей; вкладка «Жизнь» с быстрыми кнопками ожидания. Недоступные действия показаны с причиной.

Известные ограничения эвристик: одно намерение на сообщение; отрицания («не открываю») не распознаются отдельно; падежи сопоставляются по основе первого слова имени. Следующий шаг — MECH-2 (см. roadmap).

## 4. Форма истории (NARR-7)

- Выбирается при создании своей истории; пресеты создаются как арка с целью сценария.
- Редактируется владельцем во вкладке «Жизнь» (`PATCH /api/sessions/:id` с `storyShape`). Статус завершения ставится только событием хода; после финала доступно «Продолжить после финала» (`storyShape.reopen=true`).
- Для открытой жизни промпт запрещает навязывать угрозы и кульминацию.

## 5. Визуализация (VIS-1, VIS-2)

Таблицы `scene_visuals` и `visual_identities` (миграция `0014_scene_visuals`). Изображение — иллюстрация, а не канон: оно не меняет состояние и не копируется в forks/экспорт.

| Маршрут | Доступ | Назначение |
|---|---|---|
| `GET /api/sessions/:id/visuals` | чтение | Список без байтов, паспорта, конфигурация провайдера |
| `POST /api/sessions/:id/visuals` | владелец | `{ kind: scene|location|portrait, subject?, turnNumber? }` — создаёт запись `pending` из подтверждённого состояния |
| `GET /api/sessions/:id/visuals/:visualId` | чтение | Отдаёт сохранённые байты; владелец при первом просмотре запускает генерацию у провайдера; читатель public-сессии видит только готовое; `?retry=1` — повтор владельцем тем же провайдером и seed |
| `DELETE /api/sessions/:id/visuals/:visualId` | владелец | Удаление; снимает ссылку эталона |
| `PATCH /api/sessions/:id/visuals/identities` | владелец | Паспорт внешности, эталонное изображение, новый seed |

Провайдер: общий контракт `MediaProvider` (`src/lib/visual-provider.ts`) и адаптер Pollinations. По [актуальной документации API](https://github.com/pollinations/pollinations/blob/main/APIDOCS.md) генерация требует Bearer-ключ: без серверного `POLLINATIONS_API_KEY` создание и генерация недоступны, но уже сохранённые изображения читаются. Используется документированный `gen.pollinations.ai/image/{prompt}` и текущая каноническая модель по умолчанию `tongyi-mai/z-image-turbo`; пользовательский `CHRONICLE_VISUAL_MODEL` требует отдельной проверки по каталогу. Провайдер не переключается незаметно после ошибки. Ответ принимается только с поддерживаемым image MIME и размером до 8 МБ. Дневной лимит на владельца — `CHRONICLE_VISUAL_DAILY_LIMIT` (40). Отключение — `CHRONICLE_VISUALS_DISABLED=1`.

Администратор меняет глобальную модель для **новых** иллюстраций на `/system/visuals`. Сервер показывает официальные text-to-image модели из публичного каталога Pollinations и повторно сверяет точный canonical ID при сохранении через admin-only `PATCH /api/system/visual-model`. Выбор хранится в singleton-таблице `visual_settings` (миграция `0015_visual_settings`) и имеет приоритет над `CHRONICLE_VISUAL_MODEL`; переменная остаётся начальным значением до первого сохранения. Каждая запись `scene_visuals` хранит собственные `provider/model/seed`, поэтому смена настройки не меняет старые запросы и повторы. Если каталог недоступен, сохранять непроверенную модель нельзя. Некоторые модели платные, игнорируют seed или ограничивают размеры; текущий UI показывает категорию, но не гарантирует пригодность каждой модели для всех форматов. Ошибка провайдера видна владельцу без скрытого перехода к другой модели.

Приватность: промпт строится из описания места, персонажей, объектов и фрагмента повествования; длина ограничена 900 символами. Служебные ID и ключи не добавляются программно, однако авторский текст и имена могут содержать личные сведения. При ручном запуске они передаются Pollinations; режим гарантированно приватного хранения у внешнего провайдера здесь не заявляется.

Узнаваемость (VIS-2): у героя, NPC и мест есть паспорт внешности и постоянный seed. Повторяемость seed зависит от выбранной модели и не гарантируется адаптером. Эталонное изображение выбирается пользователем. Передача эталона провайдеру как reference image не реализована: для этого нужен публичный или подписанный URL исходника и модель с reference input (см. roadmap VIS-2b).

## 6. Окружение с pgvector

Текущий контракт памяти требует расширение `vector`, `pgcrypto` и векторную функцию из миграции `0006`; readiness (`/api/health`) возвращает 503, если обязательная часть схемы отсутствует или неисправна. Это намеренно сохранено при переносе: уже применённую миграцию нельзя переписывать так, чтобы старые базы получили другой смысл.

Вариант «работать без pgvector» из кандидатной ревизии отложен. Если он понадобится, его нужно спроектировать как отдельный, обратимый режим с append-only миграцией (или как отдельную pre-release схему), явным выбором backend и проверками качества retrieval. Текущая база не объявляет отсутствие pgvector совместимым режимом.
