## Методика

Chromium 1280×900, русский locale, обычное сетевое соединение одной машины без искусственного throttling. Before и after выполнены последовательными сериями по одному каноническому адресу с настоящими HTTP handlers и рабочей БД. Моки API и платные AI-вызовы не использовались. Для аккаунта создан отдельный пустой технический профиль без административных прав; тот же аккаунт используется до и после поставки. Пользовательские истории, ключи и настройки не изменялись.

Для каждой версии и каждого вида identity:

- **Первый вход, n=5:** новый BrowserContext без HTTP-кэша. Гость получает новый гостевой профиль; аккаунт использует существующую авторизованную сессию.
- **Повторный вход, n=5:** новая страница в последнем контексте с сохранёнными cookies, HTTP-кэшем и возможным состоянием service worker. Это полная навигация, а не SPA-переход.
- **Сохранение, n=10:** изменение `dailyFlashLimit` с исходного 20 на 21 и обратно, через настоящую форму. Каждая запись проверяет HTTP 200, каноническое значение ответа и значение в поле. После серии отдельный GET подтверждает исходное значение 20, отсутствие ключей и выключенный live AI. After также проверяет исходные условия до мутаций и повторный GET после восстановления в `finally`.
- **Отдельные API, n=5 на endpoint:** полное получение JSON для auth, sessions, settings, workspace с тем же профилем.

**Готовность данных** отсчитывается перед `page.goto()` и заканчивается после появления Overview и исчезновения `.overview-loading`. Она включает загрузку документа, JavaScript, React и данных. Это не FCP/LCP и не первая возможность пользоваться публичной оболочкой. **Сохранение UI** отсчитывается перед кликом до получения полного тела POST и повторной доступности кнопки сохранения. В него входит небольшой overhead Playwright/actionability; отдельный `Server-Timing` показывает серверную часть.

Здесь «первый вход» означает новый браузерный контекст, а не принудительно холодные Vercel function, pool или БД. Один Chromium-процесс используется на серию; регистрация аккаунта и чтение версии могут прогреть часть окружения. Первые чтения нового гостя также создают строки preferences/settings. Нагрузка, прогрев и маршрутизация не контролировались. Небольшая выборка позволяет описать наблюдения и структуру запросов, но не установить production SLO или точный причинный эффект для всех посещений.

## Загрузка данных и сохранение

Все значения — миллисекунды. p50/p95 вычислены линейной интерполяцией по исходным неокруглённым значениям. **p95 при n=5/10 близок к максимуму этой небольшой серии; это не оценка устойчивого хвоста production-трафика.** Диапазоны и все точки ниже сохраняют видимый разброс.

Наблюдаемая медиана сохранения сократилась на 78% у гостя и 83% у аккаунта; повторного входа — на 47% и 52%. Первый вход гостя улучшился по медиане на 28%, но сохраняет заметный разброс. Первый вход аккаунта в этой серии сократился на 52%; распределённые холодные старты и регион БД отдельно не изолированы. Первоначальная серия `a7afbb9` дала другую медиану первого гостевого входа (3098 мс); это дополнительная причина не превращать небольшие последовательные выборки в обещание SLO.

Все 20 навигаций каждой версии вернули успешные API responses; все 20 записей каждой версии подтвердили канонические значения. Ошибок JavaScript в навигационных проверках не было; просмотр сохранённых save responses также не выявил HTTP ошибок. Фоновые `/api/version`, `/api/tokens/stats` и `/api/telemetry/vitals` учитываются отдельно от цепочки синхронизации.

Заключительное чтение `/api/bootstrap` и `/api/settings` повторно подтвердило гостя/аккаунт, ноль кампаний и исходный лимит 20; bootstrap имеет `Cache-Control: private, no-store`. Сессии технического аккаунта отозваны через штатный logout-all: прежний session token больше не даёт identity аккаунта. Приватный файл browser storage state удалён после этой проверки. Пустые технические профиль/аккаунт остаются обычными записями БД; пользовательские данные и ключи не использовались.

| Подтверждённая цепочка | До | После |
| --- | --- | --- |
| Начальная синхронизация | auth → sessions/settings/workspace → auth; 5 responses | Один GET `/api/bootstrap`; подтверждено во всех 20 навигациях |
| Обычная настройка | POST settings → GET settings → auth → sessions/settings/workspace → auth; 7 responses | Один POST `/api/settings`; подтверждено во всех 20 сохранениях, без повторного чтения или полного refresh |

Удаление лишних этапов подтверждено реальными путями responses и отдельными browser-регрессиями. Счётчик наблюдает завершившиеся responses в измеряемом окне; фоновая телеметрия может добавить ответ и не считается синхронизацией.

## Публичный интерфейс во время загрузки БД

Дополнительная after-серия: по пять новых контекстов гостя и аккаунта. Сразу после DOMContentLoaded нажимается «Как это работает», ожидается открытый диалог; затем проверяется identity и завершение bootstrap.

| Режим | n | От навигации до открытой справки, p50 | Диапазон | Данные ещё загружались при открытии |
| --- | ---: | ---: | ---: | ---: |
| Гость | 5 | 654 мс | 629–689 мс | 5 / 5 |
| Аккаунт | 5 | 632 мс | 619–648 мс | 5 / 5 |

Справка действительно открывалась до ответа bootstrap во всех десяти попытках. Это отдельное подтверждение доступности публичной оболочки при продолжающейся загрузке профиля. Оно не доказывает отзывчивость каждого контрола; сохранность черновика и фокуса при задержке/смене identity проверяют изолированные desktop/mobile регрессии.

HTML TTFB основной серии остался около 120 мс: p50 до/после 120/120 мс у нового гостя и 121/125 мс у аккаунта. DOMContentLoaded p50 — 344/425 мс и 341/374 мс соответственно. Основная экономия подтверждается в цепочке получения данных и в ожидании после записи.

POST `/api/settings` сообщает `Server-Timing: app;desc="response-ready"`. Сохраняющийся разброс первого входа находится в том числе внутри серверного интервала; разделения на подключение, ожидание пула, SQL, cold start и регион в этих данных нет. Назвать конкретный из этих факторов причиной без дополнительного инструментария нельзя.
