# Гонки смены пароля и переноса гостевых кампаний — 10.10.2026

Проверен оставшийся P1 из identity/accounts: вход с ранее прочитанным хешем, параллельная смена пароля и перенос гостевых кампаний (`adopt`/claim) при отзыве или истечении сессии. Два дефекта воспроизведены до исправления и закрыты регрессионными тестами. Проверка охватывает перечисленные порядки исполнения; остальные P1 из [матрицы покрытия](testing/coverage-matrix-2026-10-09.md) сохраняются.

## Исправления и порядок операций

**Обычный выход и claim.** Раньше `logout` удалял сессию без блокировки строки аккаунта. Claim мог уже пройти защищённую проверку, ждать допуска по владельцу и затем перенести кампании после независимо завершившегося отзыва сессии. Теперь `logout` выполняет поиск аккаунта, блокировку аккаунта и удаление только своего токена в одной транзакции, соблюдая общий порядок account → session. Если отзыв завершился до защищённой проверки claim, перенос отклоняется. Если claim первым получил блокировку аккаунта, он завершает перенос, затем выход отзывает сессию. Другие устройства сохраняют свои сессии; выход с истёкшим, отсутствующим или некорректным токеном остаётся идемпотентным.

**Истечение сессии во время транзакции.** `now()` в PostgreSQL фиксирует время начала транзакции. При задержке перед финальной проверкой уже истёкшая сессия могла считаться действующей. `accountForToken` теперь сравнивает `expires_at` с `clock_timestamp()`. Регрессия устанавливает срок сессии в текущее время БД после начала claim и до его защищённой повторной проверки. Авторизация оценивается в этой проверке; тест не требует нового решения об истечении после уже авторизованной работы непосредственно перед COMMIT.

**Смена пароля.** Вход уже сравнивал прочитанный хеш с текущим хешем под блокировкой аккаунта. Изменять этот код не потребовалось. Native-тест задерживает реальный SELECT, завершает смену пароля через другое соединение и доказывает отказ старого входа без новой сессии; новый пароль успешно входит. Для двух запросов смены пароля проигравший запрос с отозванной сессией отклоняется, обе прежние сессии недействительны, принимается только пароль победившего запроса.

Production-изменения ограничены [auth.ts](../src/lib/auth.ts). Исторические миграции и ledger не изменены.

## Регрессии и доказательства

Новый [native fixture](../tests/integration/auth-races-postgres.integration.ts) использует настоящий auth service, SQL и криптографию через независимые соединения PostgreSQL. Обёртка задаёт только барьеры до/после запроса; решения об авторизации не подменяются. Восемь дочерних сценариев и родитель дают **9 runtime registrations**:

1. Ранее прочитанный хеш не выпускает сессию после завершившейся смены пароля; новый пароль работает.
2. Два запроса смены пароля сохраняют один допустимый результат и отзывают прежние сессии.
3. Обычный выход, завершившийся до защищённой проверки, запрещает claim.
4. Выход со всех устройств в том же порядке запрещает claim.
5. Смена пароля в том же порядке запрещает claim.
6. Истечение после BEGIN, но до защищённой проверки запрещает claim.
7. Уже авторизованный claim блокирует обычный выход до своего завершения; ожидание подтверждается `pg_blocking_pids`, после него проверяются перенос и отзыв сессии.
8. Actual HTTP handler возвращает 401/`IDENTITY_REQUIRED` без cookie/переноса/consumed guest/settings/account-budget эффектов для отозванной сессии; повторный выход возвращает 200, `private, no-store` и очищает HttpOnly session cookie.

Все отказавшие claims сохраняют владельца кампании, гостевые настройки и отсутствие записи `consumed_guest_profiles`. Обычный [accounts test](../tests/accounts.test.ts) дополнительно проверяет удаление истёкшей сессии, повторный выход и сохранение другого устройства.

## Изоляция и пределы

Использован новый принадлежащий проверке PostgreSQL16.15 cluster, loopback port55439, синтетические credentials, отдельная fixture DB и случайные схемы. Наследуемые DB/provider credentials очищаются до импорта приложения; тест запускается только с `CHRONICLE_RUN_AUTH_RACES_POSTGRES=1`. Проверка guard без opt-in даёт skip и не считается native pass. В [CI](../.github/workflows/ci.yml) добавлен явный opt-in step к существующему disposable PostgreSQL service; удалённый CI в этом этапе не запускался.

Fixtures исполняют **19/20** SQL migrations: immutable `0006_database_memory_search.sql` исключён из этого native runtime без pgvector. Это relational evidence гонок, не full vector replay/readiness. После прогонов fixture schemas и public tables — 0; owned сервер остановлен, listeners/processes — 0, `postmaster.pid` отсутствует (`native-schema-cleanup.log`, `native-cleanup.json`).

Проверка HTTP напрямую вызывает handler; браузерное хранение cookies, network dispatch, потеря ответа, process restart, полный внешний identity audit и прочие P1 требуют отдельных сценариев. Реальная база кампаний, платные провайдеры и deployment не использовались. Commit/push не выполнялись. Девять файлов перенесены в основной каталог после сверки девяти исходных preimages; SHA256 каждой поставленной версии совпадает с worktree (`delivery.json`). Все349 путей `src/tests` совпадают после нормализации ранее существовавших CRLF. В основном каталоге accounts/auth-handlers/identity-consistency дали **17/17**, fail/skipped/cancelled0, exit0; typecheck, lint и `check:docs` также exit0 (`main-*.log`). Предыдущие изменения проекта сохранены.
