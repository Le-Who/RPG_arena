## Снимки контрольных точек

В production проверяются ограничения быстрого снимка: 4 МиБ UTF-8, 2000 записей журнала и 1000 сущностей каждого типа. Новые положительные controls создают и разворачивают снимки ровно на каждом пределе, сравнивают полные наборы ID и буквальный текст. Байтовый пример использует кириллицу и emoji, чтобы отличать UTF-8 bytes от длины строки JavaScript. Превышение на один байт или строку не должно усекать данные.

Исходное создание уже соблюдало эти пределы, но `assertSnapshot` не проверял строковые лимиты при загрузке ранее сохранённого снимка. JSONB после чтения также считался корректным TypeScript-объектом: повреждённые envelopes, коллекции, вложенные references и нестроковые ID давали `TypeError` либо доходили до вставок SQL. Общая карта remap включала ID session и memory links, а проверка дубликатов их пропускала.

Каждый отрицательный fork получает сохранённый снимок с заново вычисленным настоящим checksum. SQL BEFORE INSERT sentinel на `game_sessions` доказывает, что ожидаемый отказ происходит до начала вставок; сравнение 15 durable tables дополнительно проверяет отсутствие последствий. Старый v1 без `agreements` и с nullable `connectedTo` имеет положительный пример. Проверка формата UUID для всех внутренних ID не вводится; строгий portable parser сохраняет собственный контракт.

Первый прерванный запуск имел SQL-опечатку fixture и не считается доказательством дефекта. Его исходный raw log был перезаписан. Позднее отдельное воспроизведение явно обозначено как reproduction, также исключено из genuine RED. Полные meaningful original runs сохранены в `checkpoint-original.log`, `checkpoint-original-nested.log` и `checkpoint-original-identity-shape.log`.

## Передача предметов и происхождение владения

Исходный `find` одновременно сопоставлял NPC key, отображаемое имя и упоминание в тексте. Чужое имя могло перехватить точный ключ, короткое имя — точное длинное имя; несколько подходящих NPC выбирались по порядку массива. Аналогичная коллизия существовала между ID и названием локации. NPC со статусом `missing` принимал предмет по устаревшей текущей локации, хотя действующая проверка присутствия такого NPC отклоняет.

Доказательства включают оба порядка строк, положительные exact-key/name/prose/current-location controls, отказы dead/missing/remote/unknown и неизменность входного snapshot. Реальный `performTurn` на мигрированной PGlite связывает inventory, world holdings, applied changes и каноническую память с буквальными ожиданиями; сгенерированный ответ здесь синтетический.

Принятая inventory-операция `add` передаёт только `{name, quantity}`. При двух одноимённых holdings исходный код уменьшал первую запись и создавал память о возврате, хотя источник не определён. Коррекция сохраняет неопределённые holdings и прежнюю ownership memory, принимая саму подтверждённую acquisition. Существующий уникальный name-based return, включая NPC/courier из другого места, сохраняется: новый протокол provenance или запрет удалённой доставки не вводится.

## Ротация ключей: расширение без исправления production

Все 12 новых проверок прошли на исходном `rotateSecrets`. Настоящие SQL и AES-GCM проверяют каждое защищённое поле отдельно, переходы Gemini array↔SQL NULL, удаление профиля перед UPDATE и сохранение полной строки при конфликте: остальных ключей, timestamps, постороннего поля и следующих профилей.

Смешанные keyset batches содержат пустые, уже активные, старые зашифрованные и legacy plaintext значения. Без явного plaintext opt-in ранее завершённые профили остаются пригодными; разрешённый повтор продолжает работу. Ошибка расшифровки последнего ключа сохраняет целиком проблемный профиль при размерах пакета 1 и 2. Исправление одной неисправной записи позволяет завершить повтор без повторного шифрования прежних успешных профилей; дальнейший запуск только с active encryption key выполняет ноль обновлений. Тесты также проверяют owner binding.

Конкурентное изменение вставляется перехватом query непосредственно перед настоящим UPDATE. Это доказательство CAS и последствий отказа в одном процессе, а не native multi-connection contention. Глобальная транзакция между всеми профилями не предполагается.

## Границы доказательств и следующие пробелы

PGlite исполняет настоящие SQL и все numbered migrations, включая vector/pgcrypto в checkpoint/turn fixtures. Он не доказывает native PostgreSQL contention, COMMIT/disconnect/crash или готовность deployed environment. Crypto/CAS fixtures используют минимальную таблицу со всеми затрагиваемыми колонками. Strict portable validation, wire contracts и historical migrations сохраняются.

Контроль формы JSON не является исчерпывающим parser всех доменных scalar fields. Подтверждение синтетического рассказа не измеряет качество live модели. Протокол source-holder identity для произвольной acquisition, native crash/commit boundaries, независимая semantic evaluation и оставшиеся field/browser measurements требуют собственных тестов. Существующие MEM/NARR/SEC/ECO/UX/PERF task IDs и приоритеты сохраняются.
