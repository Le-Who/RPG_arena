# Необязательные аккаунты и административные границы

Серверный контракт интеграции revisions от 23 сентября 2026. Полная интеграция интерфейса и итоговые browser-проверки отслеживаются в [отчёте](revision-integration-review-2026-09-23.md); наличие этого документа не означает завершение всего релиза.

## Гость остаётся полноценным пользователем

Для создания и продолжения кампаний регистрация не требуется. Гость может управлять своими историями, личной памятью, BYOK-настройками и экспортом. Его доступ связан с секретной cookie этого браузера: очистка cookie может лишить доступа. Публичный профильный ID — хеш, не credential.

При регистрации текущий профиль закрепляется за аккаунтом: кампании и зашифрованные настройки сохраняют свои ID и привязку. Старый гостевой токен становится недействительным для этого профиля, а браузер получает новый пустой гостевой профиль. После выхода истории аккаунта не появляются у гостя.

При входе в существующий аккаунт новые гостевые кампании **не переносятся автоматически**. Сервер возвращает их количество; UI должен предложить отдельное подтверждение. Отказ ничего не меняет: после выхода посетитель снова видит оставленные гостевые кампании. Подтверждение переносит кампании, закрывает прежний гостевой доступ и выдаёт новый пустой гостевой профиль. Гостевые ключи и настройки не заменяют настройки существующего аккаунта.

## Сессии и пароли

Сессия действует 30 дней без скользящего продления. Выход отзывает текущую сессию; выход со всех устройств и смена пароля отзывают все сессии, включая текущую. На сервере хранятся хеши случайных токенов, не их исходные значения. Положительного межзапросного кэша авторизации нет.

Логин — 3–40 латинских букв, цифр, точки, дефиса или подчёркивания; первый символ — буква, цифра или подчёркивание. Регистр нормализуется. Пароль — от 12 символов до 256 UTF-8 байт. Scrypt использует явно заданные, версионированные параметры. Самостоятельное восстановление забытого пароля не реализовано; интерфейс не должен обещать email/recovery-функции, которых нет.

## Кто является администратором

`CHRONICLE_ADMIN_ACCOUNT_IDS` — серверный список UUID аккаунтов через запятую. Пустой список означает отсутствие административного доступа для всех. Не используйте логин, имя профиля, `guest:<digest>`, localStorage или «первого посетителя» для назначения роли.

Оператор получает свой `identity.account.id` из авторизованного `GET /api/auth/me`, указывает его в окружении и перезапускает **все web и worker экземпляры**. Не копируйте cookie, пароль или session token в конфигурацию роли и диагностические инструкции.

После входа в нужный аккаунт откройте консоль браузера на сайте и выполните:

```js
fetch('/api/auth/me', { credentials: 'same-origin' }).then(r => r.json()).then(({ identity }) => console.log(identity.account?.login, identity.account?.id))
```

Проверьте, что показан логин `63174`, и добавьте выведенный UUID в `CHRONICLE_ADMIN_ACCOUNT_IDS` через запятую к уже назначенным UUID. После перезапуска web/worker снова откройте `/api/auth/me`: `identity.isAdmin` должен быть `true`. Сама переменная с UUID не является секретом, но менять её могут только операторы развёртывания.

| Функция | Обычный гость / аккаунт | Администратор |
|---|---|---|
| Собственные кампании, настройки, память, журнал, BYOK, экспорт | Доступно | Доступно для своего пространства |
| `/system` | 404 | Доступно |
| `/api/system/*` | 403 | Доступно; управление не расширяет ownership автоматически |
| `/system/visuals` и `/api/system/visual-model` | 404/403 | Выбор модели Pollinations для новых иллюстраций; запись в БД проверяется по каталогу, прежние изображения сохраняют модель |
| Developer/Jev API и shadow pilot | Запрещено, даже если старый enabled-флаг сохранён | Разрешено для административного владельца |
| Технические narrative diagnostics | Запрещено | Дополнительно требуется владение кампанией |
| `/blueprint` | Публичная справка | Та же справка |
| `/api/health` | Минимальное `{ok}` | Тот же публичный минимальный ответ |

Административная роль не даёт права играть за другого пользователя, читать все тексты его историй или менять его API-ключи. UI скрывает недоступные пункты, но настоящая защита находится в серверных обработчиках.

## Origin и ограничения попыток

Все изменяющие API-запросы требуют совпадающий Origin. `CHRONICLE_PUBLIC_ORIGIN`, если задан, содержит точный origin без пути и завершающего `/`, например `https://stories.example.com`. Иначе используется origin URL запроса. Это важно за HTTPS reverse proxy: настройте канонический origin, не ослабляйте проверку до произвольного same-site адреса. CLI-клиентам нужно явно передавать соответствующий Origin; общие smoke-helper уже это делают.

По умолчанию заголовкам адреса клиента не доверяем: используется один консервативный общий rate-limit bucket. Регистрация ограничена 10 попытками за 15 минут; остальные изменяющие auth-действия, кроме обычного выхода, — 30 попытками на действие за 15 минут. Изменение логина не создаёт новый bucket. Обычный выход остаётся доступен при исчерпании лимита.

`CHRONICLE_AUTH_TRUSTED_CLIENT_HEADER` можно задать только при наличии доверенного ingress, который **перезаписывает** выбранный заголовок, и при закрытом прямом доступе в обход него. Иначе оставьте параметр пустым. Общий bucket может ограничивать доступность при общей нагрузке; это явная граница исходной конфигурации, не обещание готовности массового публичного сервиса.

## Перенос профиля при активной работе и после аварии

Регистрация/перенос не происходят, пока с гостевым профилем выполняется работа. Короткая транзакция регистрирует `owner_activity`, а запрос, поток хода или worker удерживает запись до завершения реальной работы. Это совместимо с transaction pooling: соединение и DB-транзакция не удерживаются во время AI-запроса. Session-level advisory locks для этого не используются.

Время жизни активности намеренно не истекает по таймеру: поздний ответ провайдера не должен пересечь смену владельца. Авария процесса или ошибка удаления записи могут оставить orphan. Такая запись блокирует регистрацию/перенос соответствующего гостя, но не обычную игру, настройки или вход в существующий аккаунт.

Для восстановления оператор сначала останавливает и дожидается завершения **всех** web/worker/планировщиков, использующих эту БД. Затем смотрит конкретные записи:

```sql
SELECT id, owner_id, created_at FROM owner_activity ORDER BY created_at;
```

Только после проверки, что работы действительно больше нет, удаляются точно выбранные orphan ID, после чего сервисы запускаются снова. Не очищайте таблицу по возрасту, не запускайте автоматический reset, не удаляйте записи при работающей реплике. Публичного endpoint для такого сброса нет. Это ручное восстановление — известное ограничение текущего решения.

## Проверки и границы

`npm test` включает изолированные lifecycle, API, роли, отзыв сессий, постоянные tombstone гостевых токенов, Origin и rate-limit проверки. Отдельный opt-in native PostgreSQL тест проверяет конкуренцию настоящих соединений и отсутствие удерживаемых session locks во время provider-паузы. Его БД — временная fixture, не пользовательская; отсутствие pgvector в этой fixture не считается успешной полной production-миграцией. Полный ledger с расширениями проверяется отдельно в PGlite.

Настройка тестового администратора для Jev smoke описана в [эксплуатации story experience](story-experience-operations.md). Нельзя запускать эти fixture-утилиты с production БД или keyring. Live AI, внешний аудит безопасности, публичный deployment и массовая нагрузка не выдаются за выполненные локальными тестами.
