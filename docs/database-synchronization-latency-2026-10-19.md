# Задержки загрузки пространства и сохранения настроек

Дата: 19 октября 2026. Область: начальная загрузка, обновление пространства, настройки и общий допуск запросов к данным владельца.

## Причины

Задержка складывалась из последовательных сетевых этапов и повторных служебных SQL-запросов. Это происходило и у гостя без историй: отсутствие записей не отменяло проверки профиля, допуска работы и загрузки настроек.

1. `AppShell.refresh()` сначала запрашивал `/api/auth/me`, затем параллельно `/api/sessions`, `/api/settings`, `/api/workspace`, затем ещё раз `/api/auth/me`. Данные появлялись после трёх последовательных HTTP-этапов. Последняя проверка защищала от смешивания профилей и не могла быть просто удалена.
2. `SettingsForm.save()` отправлял POST настроек, игнорировал возвращённые канонические значения, перечитывал настройки и ожидал полный `refresh()`. Одна обычная настройка требовала **7 HTTP-запросов в 5 последовательных этапов**. Чистые дочерние формы сами не записывались; основное ожидание возникало в родительской форме.
3. Прокси проверял `consumed_guest_profiles` даже перед отдачей публичной оболочки с корректной по формату cookie. Недоступность базы блокировала обычную навигацию до выполнения страницы.
4. Каждая регистрация работы владельца выполняла четыре обращения: BEGIN, advisory lock, INSERT `owner_activity`, COMMIT. Эти операции повторялись для каждого запроса каскада. Очистка durable activity была отдельной необходимой операцией.
5. Каждое разрешение identity аккаунта последовательно читало аккаунт/сессию и потреблённый гостевой профиль. Обычная проверка также загружала password hash, который нужен только операциям с паролем.
6. Чтение настроек пространства всегда делало INSERT ON CONFLICT перед SELECT, включая давно существующие профили.

Общий допуск используется также при чтении кампаний и панелей, изменении профиля, избранного, предпочтений чтения и других защищённых действиях. Поэтому его стоимость проявлялась за пределами страницы настроек. Полное обновление пространства происходило и при возвращении фокуса окна, смене аккаунта и после отдельных мутаций.

## Изменения

| Путь | Прежде | Теперь |
| --- | --- | --- |
| Начальная загрузка / полный refresh | 5 HTTP-запросов, 3 последовательных этапа | Один GET `/api/bootstrap` |
| Сохранение обычной настройки | 7 HTTP-запросов, 5 последовательных этапов | Один POST `/api/settings`, канонический ответ после записи |
| Identity аккаунта | Два последовательных SQL-запроса | Один свежий SQL-запрос, без password hash |
| Допуск работы владельца | Четыре обращения к БД | Один атомарный autocommit statement |
| Чтение существующих workspace preferences | INSERT ON CONFLICT + SELECT | SELECT |
| Тёплый POST настроек, без прокси | Гость: 12, аккаунт: 16 SQL-обращений по прежней цепочке | Гость и аккаунт: 8, измерено на реальном handler с PGlite |

`/api/bootstrap` разрешает identity под общим допуском владельца и загружает список кампаний, публичную проекцию настроек и preferences с явным owner ID. Перед ответом identity проверяется повторно. Ответ имеет `private, no-store`; клиент проверяет соответствие владельца workspace и всех кампаний. Это согласованный по principal пакет, а не обещание транзакционного снимка всех таблиц.

Сохранение использует UPDATE RETURNING. После UPDATE остаётся свежая проверка identity: оптимизация убирает повторный SELECT настроек, сохраняя прежнюю границу отзыва сессии. Интерфейс принимает подтверждённые значения без перезагрузки кампаний. При сохранении изменённого рассказчика выполняется одно целевое чтение итоговой проекции настроек, поскольку дочерняя форма также меняет `useLiveAI`; остальные изменения не запускают этот запрос.

Публичная страница проверяет формат гостевой cookie без обращения к базе. Восстановление потреблённой гостевой cookie остаётся на границах `/api/bootstrap`, `/api/auth/*` и серверных административных страниц. Обычные API разрешают свежую identity в обработчиках и отклоняют потреблённый профиль; они не добавляют отдельный SQL-запрос в прокси и не создают конкурирующие случайные cookie при параллельной загрузке.

Допуск владельца использует материализованный CTE с transaction advisory lock перед INSERT durable activity. Autocommit сохраняет блокировку до фиксации записи, затем освобождает соединение. Длительная работа и внешние вызовы не удерживают транзакцию. Вложенные операции сохраняют общий допуск до завершения последней ссылки; ошибка очистки по-прежнему блокирует перенос владельца.

Первое получение identity не перемонтирует уже открытое публичное содержимое. Устаревшие ответы после смены профиля игнорируются; ответ загрузки не отменяет более новое сохранение. При 401 очищаются прежние приватные данные и ссылка на identity. Новый профиль получает свои настройки даже при совпавшем по времени сохранении старого профиля. Ввод, сделанный во время сохранения, остаётся несохранённым черновиком; ошибка записи не объявляется успехом.

Комната начинает первое чтение кампании после получения identity. Это исключает гонку восстановления гостевой cookie при прямом переходе по ссылке на открытую историю. Если bootstrap недоступен, комната показывает ошибку и повтор загрузки профиля; после восстановления не остаётся на старом 401. На production build проверены desktop и mobile, включая повтор после 503.

В существующую необязательную телеметрию добавлен `API_BOOTSTRAP`. Старые метрики сохранены для исторических выборок. Передаётся только числовая длительность и разрешённый шаблон страницы; идентификаторы профиля и содержимое историй не добавлены.

## Проверка и границы доказательств

Регрессии сначала воспроизвели лишние запросы, зависимость публичной страницы от БД, повторную запись preferences и потерю последней проверки отзыва сессии после перехода на RETURNING. После исправлений focused-наборы проходят: [identity](../tests/identity-latency.test.ts), [bootstrap](../tests/workspace-bootstrap.test.ts), [каноническое сохранение и отзыв сессии](../tests/settings-save-latency.test.ts), [клиентская граница профиля](../tests/ui-identity.test.ts), [метрики](../tests/performance-report.test.ts).

Браузерные проверки выполняются на настоящих React-компонентах с изолированными синтетическими API:

- `node --import tsx scripts/workspace-latency-browser.ts`: 12 desktop/mobile сценариев, включая доступность справки и редактирование истории при задержанном bootstrap, сохранность ввода/фокуса, гонки identity/сохранения, очистку после 401 и повтор после ошибки.
- `node --import tsx scripts/settings-latency-browser.ts`: 10 сценариев; один POST для обычной настройки, отсутствие полного refresh, сохранность новых правок/ключа, повтор после 503, одно целевое чтение после изменения рассказчика и отказ запоздавшему чтению после удаления ключа. Последняя гонка воспроизведена в RED и проверена в GREEN на desktop/mobile.
- `node --import tsx scripts/settings-draft-p2-browser.ts`: 22 проверки существующих черновиков, канонических ответов, конфликтов и закрытия формы.
- `node --import tsx scripts/web-vitals-lifecycle-p2-browser.ts`: 25 проверок privacy, lifecycle и ограничения телеметрии.

TypeScript, ESLint и production build Next.js 16.4.2 проверены на поддерживаемом Node 22.23.2. Сборка выполнена в отдельной копии без `.env`, с недоступным синтетическим адресом БД и очищенным окружением. HTTP-проверка этой сборки получила 200 для `/`, `/worlds`, `/settings`, `/api/version` с существующей гостевой cookie. На ней также прошли `ui-controls-browser.ts` и `story-experience-browser.ts` с API fixtures.

Итоговый `npm test`: **1241/1241**, fail/cancelled/skipped/todo — 0. После последних изменений proxy отдельно прошли 24 проверки bootstrap, owner activity, версий и portable body limits. Новая проверка последнего отзыва сессии наблюдалась в RED и GREEN; итоговые focused identity/settings/bootstrap/client — 14/14 до добавления отдельного cookie-race случая, который также вошёл в полный прогон. Финальные typecheck/lint/docs и build — exit 0. SHA256 всех 241 файлов приложения и конфигурации совпал с изолированной сборочной копией.

Первый полный прогон выше относится к исходному рабочему дереву, включая независимую незавершённую интеграцию изображений. Для поставки создан отдельный release worktree от `7b1981b`, без этой интеграции, изменений `.env`, схемы и миграций. В нём штатный полный `npm test` прошёл **1232/1232**, fail/cancelled/skipped/todo — 0; повторные typecheck/lint/build и production HTTP/browser smoke — exit 0. Новые 12 workspace и 10 settings браузерных сценариев и существующие 22 settings-draft включены в CI. Устаревшее ожидание текста offline fixture согласовано с действующим интерфейсом; CI сохраняет фактические каталоги PWA/retry артефактов.

Локальные артефакты: `output/db-latency-2026-10-19/`, `output/live-release/`, `output/playwright/workspace-latency/`, `output/playwright/settings-latency/`. Снимок прежнего браузерного поведения: `output/playwright/workspace-latency/original-result.json`.

Эти проверки устанавливают структуру запросов, корректность handler/state и поведение браузера. Они не измеряют рабочую базу или платных провайдеров. Независимая native PostgreSQL concurrency-проверка не выполнялась: локальные PostgreSQL и Docker отсутствуют. Для неё сохраняются существующие opt-in интеграционные тесты; PGlite не заменяет проверку нескольких PostgreSQL-соединений.

Если после развёртывания остаётся значительная задержка, нужны замеры холодного и тёплого `/api/bootstrap` и POST настроек на рабочем окружении: Resource Timing вместе с `Server-Timing`, регион приложения относительно БД, время установки соединения, ожидание пула и включённый `CHRONICLE_AUTO_MIGRATE`. Эти факторы остаются гипотезами до таких измерений; локальный HTTP smoke не доказывает production latency. Реальную БД, ключи провайдеров и развёртывание эта работа не затрагивает. Новая схема хранения и миграции для исправления не требуются.
